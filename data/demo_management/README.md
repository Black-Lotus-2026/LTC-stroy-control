# Сценарный контрольный пример

Все данные в этой папке условные. Наблюдения двух камер — синтетический replay, а изображения `/demo_management/camera-1.svg` и `camera-2.svg` — иллюстративные схемы. Кадры реального объекта, CV-модель, рыночные ставки и доступность техники не проверялись. Подтверждение блокировки в демо тоже условное.

## Входы и воспроизведение

`baseline.json`, `camera_unavailable.json`, `slack.json`, `expensive_action.json` — полные `ManagementSnapshot`, версия 1.0. Фиксированный момент анализа: `2026-10-16T05:00:00Z` (08:00 Москвы). Демо project_id — `00000000-0000-4000-8000-000000000001`; при загрузке через API сервер использует доступный текущему пользователю объект и материализует отдельные demo зоны/камеры. UUID камер и зоны стабильно выводятся из project_id через uuid5. Для чужого project_id fixture не обходит серверную проверку доступа.

Из корня репозитория:

```sh
cd backend
.venv/bin/python -m pytest tests/test_management_schedule.py tests/test_management_costs.py -q
.venv/bin/python - <<'PY'
import json

```

`expected_results.json` содержит рассчитанные контрольные значения и hash snapshot. `generate.py` воспроизводит JSON из `make_demo_snapshot`; запускать из корня репозитория через `backend/.venv/bin/python data/demo_management/generate.py`. Функция `make_demo_snapshot(project_id, episode)` подставляет реальный разрешённый сервером идентификатор объекта без изменения числовых допущений.

## График и календарь

Опорный прогноз: A 0–8, B 12–20, C 20–28, D 0–24, M 28 рабочих часов. Связи только A→B→C→M и D→M; D независима от A. A полностью заблокирована до восстановления. Вмешательство восстанавливает ресурс через 2 или 4 рабочих часа, без действия — через 8. Это введённые сценарии, не прогноз вероятностей или доступности.

В топологическом порядке `start = max(0, earliest_start, recovery для A, finish каждого предшественника + lag)`; `finish = start + remaining_work_hours`. Сначала рассчитывается опорный прогноз с recovery=0, затем сценарий. Запас до B поглощает первые 4 часа. Согласованный срок хранится отдельно; `deadline_variance_work_hours` и `incremental_delay_work_hours` имеют разные базы сравнения. Сохранённые плановые даты не меняются. Завершённые задачи сохраняют actual_finish; их remaining_work_hours должен быть 0.

Поддерживается один календарь дневной смены, FS-связи с неотрицательным лагом и DAG. В примере рабочая смена 08:00–16:00, понедельник–пятница, Europe/Moscow. Добавочные рабочие даты и праздники заданы явно, конфликтующие исключения и ночные смены отклоняются. Даты результатов UTC. Рабочие часы — прошедшие секунды внутри локальных смен / 3600. Выходные не прибавляются к рабочим часам. Ресурсной оптимизации, ночных смен, SS/FF связей и нескольких календарей нет; горизонт ограничен 200 годами.

## Деньги

`total = idle + extension + intervention + other_explicit`.

Простой = оплачиваемое количество × доля простоя × ставка × длительность в единицах ставки. Учитываются только явно оплачиваемые затронутые ресурсы. Интервал начинается не раньше опорного старта заблокированной задачи и ближайшего рабочего старта, заканчивается при восстановлении ресурса. Прошлые затраты до as_of не входят в будущий эффект.

Продление начисляется один раз для выбранной контрольной точки на интервал между опорной и сценарной датой. В примере ставка явно исключает отдельно учтённые экскаватор и бригаду. Ставки разбиваются на непересекающиеся интервалы действия [valid_from, valid_to). work_hour исключает нерабочее время; work_day делится на длительность настроенной смены (не всегда 8); calendar_day пропорционален прошедшим секундам / 86400, включая выходные. При переходах летнего времени сутки не искусственно округляются до календарной даты.

Все вычисления Decimal (precision 64); каждый тарифный сегмент округляется до копеек ROUND_HALF_UP, затем складывается. Разовые затраты реакции входят один раз. Точные дубликаты ресурса/явной статьи/ставки устраняются, конфликтующие определения отклоняются. Совпадающие группы разных статей или неподтверждённое исключение ресурсов из продления приводят к partial и отсутствию общего итога; отдельные компоненты видны. Разные валюты отклоняются без автоматического курса. Неизвестные ставки, пробелы тарифа, отсутствующий профиль ресурсов остаются null и перечисляются в missing_inputs. Неизвестная статья не подменяется нулём.

| Сценарий | Простой | Продление | Действие | Всего | Перенос M |
| --- | ---: | ---: | ---: | ---: | ---: |
| fast, 2 ч | 24 000 ₽ | 0 ₽ | 20 000 ₽ | 44 000 ₽ | 0 ч |
| late, 4 ч | 48 000 ₽ | 0 ₽ | 20 000 ₽ | 68 000 ₽ | 0 ч |
| no_action, 8 ч | 96 000 ₽ | 16 000 ₽ | 0 ₽ | 112 000 ₽ | 4 ч |

Цена бездействия относительно fast = 112 000 − 44 000 = **68 000 ₽ условного сокращения будущих дополнительных затрат**. Это не фактически достигнутая экономия. Сравнение сохраняет знак и допустимо только для полных результатов одного snapshot, валюты и версии калькулятора.

В `camera_unavailable` вторая камера offline, модель unavailable, блокировка hypothesis; арифметика остаётся условной, доказательства ограничены. В `slack` B начинается не раньше 16, поэтому все три варианта не сдвигают M; no_action стоит 96 000 ₽. В `expensive_action` мобилизация стоит 150 000 ₽; fast = 174 000 ₽, no_action = 112 000 ₽, эффект = **−62 000 ₽**.

## Граница адаптера

`ScenarioCalculator.calculate(snapshot, scenario) -> ScenarioResult` объявлен в `app.services.management.economic_adapter`. `get_calculator()` возвращает текущую реализацию. Модуль капитана подключается в этой точке без изменения API, UI и ролей. Калькулятор не вызывает LLM и не принимает деньги из её ответа. Каждая денежная строка содержит формулу, исходные числа, источник и интервал. `input_hash` — SHA-256 полного неизменного snapshot (одинаков для всех трёх результатов); выбранный сценарий обязан совпадать с записью snapshot.

Фактические проверки 16 октября 2026: 39 тестов графика и экономики passed в локальном backend/.venv; точный пример воспроизведён отдельно. Проверяется сохранение копеек и знака разницы при больших разрешённых входах (сравнение тоже использует Decimal precision 64). Это проверки условных данных, не результаты полевого пилота.

Дополнительно 27 изолированных HTTP/БД/worker тестов в `backend/tests/test_management_api.py` passed; объединённый запуск трёх файлов — **66 passed**. SQLite с проверкой внешних ключей, реальный `execute_run` вызывается через тестовый синхронный dispatch, внешние LLM запрещены. Проверены доступ к чужим данным, идемпотентность, повтор доставки worker, срок аренды, отказ очереди, перезагрузка сохранённых результатов, null ставок, UUID/статусы/дедупликация инцидента и время съёмки. Сохранённые правила/классы/порог детекции и ставки имеют приоритет над полями клиента; `truck` преобразуется в `dump_truck`, посторонние ссылки удаляются, чужие ставки ресурсов и продления отклоняются. Эта проверка не заменяет PostgreSQL-миграции, настоящий Celery broker или проверку живого провайдера.

Локальный замер: Python 3.12.2, Darwin arm64, 10 последовательных прогонов по 3 сценария baseline, без API/БД/LLM. Время каждого полного набора, мс: 1.248, 1.135, 1.053, 0.959, 0.921, 0.917, 0.905, 0.904, 0.905, 1.069. Диапазон 0.904–1.248 мс, среднее 1.002 мс. Каждый прогон проверил точные итоговые суммы. Это измерение на маленьком демонстрационном графе, не нагрузочный тест.
