# Контракты управленческого анализа

Версия схемы `1.0`, baseline разработки `817f7bf`. Существующий стек: FastAPI, SQLAlchemy, PostgreSQL, Redis/Celery, React/TypeScript. Схема: `backend/app/schemas/management.py`.

## Последовательность

Авторизация объекта → нормализация ссылок по БД → неизменный snapshot → очередь → анализ оснований → чистый калькулятор трёх сценариев → предложение действий → проверка → сохранённая карточка. Изменение входов создаёт новый запуск с `parent_run_id`, история не пересчитывается.

`ManagementRun` хранит snapshot, hash, режим, результаты, автора, сроки, бюджет вызовов и статус. `ManagementRunStep` — отдельные этапы с provider/model/prompt_version, временем, числом вызовов, usage, ссылками на контекст и ошибками. `TaskDependency` хранит явные FS связи версии графика; профиль хранится в `ProjectSettings.extra.management_profile` с автором и временем. Обновление профиля сохраняет остальные настройки объекта.

Активный снимок защищён уникальным `active_key`. Идемпотентный ключ связан с пользователем и объектом; повтор с другим телом даёт 409. Worker атомарно захватывает только queued запуск, повтор доставки не исполняет роли заново. Каждое сетевое обращение резервируется в БД до отправки. Истечение аренды и запись результата используют блокировку строки: поздний ответ не может оживить завершённый запуск. API фиксирует ошибку отправки в очередь; чтение не выполняет скрытого повторного запуска.

## Три роли

| Роль | Контекст и выход | Проверка |
|---|---|---|
| `evidence` | Снимки, время, исправность камер/модели, зона, правило → `EvidenceAssessment` | Только допустимые source_refs, наблюдения из каталога входов; нельзя повысить доступность или убрать обязательную проверку |
| `actions` | Проверенные основания, три разрешённых сценария и результат калькулятора → `DecisionProposal` | Только известные scenario_id/metric_refs, проверка минимальных затрат по объявленному условному критерию, сохранение гипотез и недостающих данных |
| `reviewer` | Входы, основания, калькулятор, предложение и ошибки валидатора → `ReviewResult` | Нельзя объявить passed при известных нарушениях; проверяется полнота ограничений |

Каждая роль имеет отдельный prompt, JSON-схему и реальный вызов адаптера при доступном LLM. Это последовательные роли, не три названия одного ответа. Адаптер `Provider.complete` заменяем; текущий `OpenRouterProvider` использует фиксированный HTTPS endpoint, строгую JSON Schema через response_format=json_schema, маршрутизацию require_parameters и последующую проверку Pydantic.

Расчёт — исполняемый код, не роль LLM. `ScenarioCalculator.calculate(snapshot, scenario) -> ScenarioResult` и `compare_scenarios` в `economic_adapter.py` — точка интеграции модуля капитана. Доступного модуля капитана в baseline не было. Численные итоги берутся только отсюда. LLM ссылается на метрики вместо записи собственных сумм; числовые утверждения в свободном тексте отклоняются. Методика, округление, рабочий календарь и точный пример: [расчёт](../data/demo_management/README.md).

У модели нет произвольного HTTP, SQL, файловой системы или действий от имени пользователя. `tool_refs` — журнал подготовленных сервером данных (`snapshot:evidence`, `snapshot:rule`, `calculator:scenario_results`, `validator:proposal`), а не заявления о самостоятельном выполнении инструментов моделью. Текст источников передаётся как `untrusted_data`; инструкции внутри него не меняют права и схему. Model tool_calls/refusal отвергаются.

Ограничения: до 6 зарезервированных вызовов, одно исправление невалидного ответа на весь запуск, 90 секунд анализа, до 20 секунд на запрос (connect до 3), 1 500 выходных токенов, контекст до 48 KB, HTTP ответ до 64 KB, JSON роли до 24 KB. HTTP повторов и редиректов нет. Ожидание очереди по умолчанию 300 секунд. Каждый из трёх отказов сохраняется; бесконечного цикла нет.

В deterministic режиме этапы LLM имеют `skipped`, а `generation=deterministic`. Правиловая проверка может пройти, но не отображается как независимая LLM экспертиза. При отказе провайдера калькулятор сохраняется, соответствующий шаг `failed` и запуск `partial`; успешный `effective_mode=llm` требует всех трёх настоящих ответов. Арифметика от режима LLM не зависит.

## Авторитетные данные и доступ

Management endpoints требуют активного пользователя, владельца объекта или администратора; viewer не пишет. Для вложенных incident/task/frame/camera/rate/parent проверяется объект. Реальное наблюдение читается из `Frame` и завершённого `AnalysisRun`, canonical class определяется через `ObjectClass` и detector_labels. Применяются сохранённые пороги и `WorkRequirement`, а не произвольное утверждение клиента. Недоступная модель не подтверждает отсутствие техники.

Правило требует сохранённого `RuleSet`, связи с work type и поддерживаемого требования presence/min_count=1. Неподдерживаемое правило отклоняется. Даты и ставки из БД нормализуются и повторно валидируются. Инцидент должен соответствовать зоне и заблокированному ScheduleTask. Неизвестные источники клиента не становятся доказательствами. Ручные сценарные допущения остаются ручными; пользовательское подтверждение блокировки не доказывает фактическую производительность.

Demo использует стабильные UUID зоны/камер, отдельный инцидент и явную маркировку replay. Изменение сценария не создаёт ещё один инцидент. Demo evidence не допускается в user профиль. Старый путь инцидентов также исправлен для UUID, авторизации, project_id, статуса, времени, пустых ответов, повторов и model unavailable; это не означает завершённый аудит безопасности всего приложения.

## API

Все пути ниже имеют префикс `/api/v1` и Bearer auth.

| Метод и путь | Назначение |
|---|---|
| GET `/projects/{id}/management/demo?episode=baseline` | Явный demo snapshot; также camera_unavailable, slack, expensive_action |
| GET/PUT `/projects/{id}/management/profile` | Сохранённый профиль; PUT `{snapshot}` |
| GET/PUT `/projects/{id}/schedule/dependencies` | Явные FS связи версии графика |
| POST `/management/runs` | `{snapshot, mode, idempotency_key, parent_run_id}` → 202 |
| GET `/management/runs/{id}` | Неизменный расчёт и текущий статус связанного инцидента |
| GET `/management/runs/{id}/trace` | Журнал этапов без секретов |
| GET `/projects/{id}/management/risks` | До 100 запусков с флагом последнего для инцидента; это история, не сумма независимых рисков |
| GET `/incidents/{uuid}/inaction-cost` | Кривая затрат бездействия по snapshot этого случая; без LLM/записи, проверка объекта |
| PATCH `/incidents/{uuid}` | Подтверждённое сервером изменение статуса существующего инцидента |

Схемы запросов видны в `/docs`. Задачи графика имеют локальный id в snapshot и необязательный `schedule_task_id` для привязки к БД. Decimal передаётся строками. Поддерживается один дневной календарь, DAG и FS лаг; ограничения расчёта описаны в методике. Универсальной ресурсной оптимизации, полного редактора графика и проверки выполнения поручений здесь нет.

`IncidentCost.tsx` подключён к списку отклонений, фотоархиву, отчётам и уведомлению. Кнопка открывает мини-окно; `inaction_curve.py` считает точки через существующий адаптер калькулятора. Старый `ManagementPanel.tsx` сохранён в исходниках, но не подключён к основному UI. Контракт, формула и проверки: [simple-cost-ui.md](simple-cost-ui.md).
