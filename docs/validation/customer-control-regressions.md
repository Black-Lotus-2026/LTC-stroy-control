## Что проверено

- Два заказчика и два подрядчика с пересекающейся географией не получают
  взаимный доступ через ID, старую глобальную роль admin или поддельный контекст.
  Если переданы оба контекстных заголовка, членство и назначение должны
  соответствовать друг другу. Discovery и отправка уведомлений используют
  собственный актуальный контекст получателя.
  Отзыв членства/назначения закрывает старый JWT, оригиналы, GET/HEAD/Range,
  доказательства и ранее сформированные отчёты.
- ПТО готовит редакции и пакеты, но не утверждает требования в контексте инженера.
  Собственный материал от подрядчика нельзя утвердить сменой контекста или отзывом
  назначения. Исключение §4.4 для совмещения исключительно у заказчика проверено
  отдельно: разрешённая самопроверка оставляет явную отметку в аудите.
  Прораб не меняет контроль, не принимает устранение и не удаляет доказательства.
  Подтверждение, работа, подача, возврат, новая подача и независимая приёмка
  проверены через HTTP. Открытый спор блокирует приёмку.
- Повторные команды и загрузки идемпотентны. Две вкладки и два конкурентных
  наблюдения проверены на PostgreSQL. Состояние ожидания приёмки остаётся
  открытым для защиты от дублей.
- Оригиналы и точные страницы ППР доступны только в соответствующем контексте.
  Изменение кандидата и новый выпуск не переписывают исторические основания.
  SQL guards сохраняют отправленные manifests, их состав, оригиналы и
  завершённые страницы; digest артефакта старой страницы допускает заполнение
  только один раз.
- Общая демонстрация использует явный manifest. Неизвестные старые документы,
  записи, случаи и фотографии сохраняются, но не публикуются автоматически.
  Отзыв manifest закрывает GET/HEAD/Range; записи и файлы остаются на месте.
- Миграционный rehearsal выполняет `1600 → 2000`, сравнивает исходные IDs,
  роли, SHA256, storage keys, статусы и даты, затем делает `pg_dump`, удаляет
  только случайную тестовую схему, восстанавливает её и сравнивает снова.
  Старые открытые дубли сохраняют статусы и получают provenance в ledger.

## Проверка интерфейса

Реальный QA API на `127.0.0.1:8991` использует отдельную SQLite и private storage.
Все QA accounts имеют глобальную роль viewer; рабочие права заданы явными
назначениями. Проверены три кабинета, защищённые изображения, оригинал ППР,
доступный документный контекст ПТО, два подрядчика у управляющего и только один
у прораба. Проверены уведомление и переход из него в разрешённое дело,
обязательные основание/подтверждение остановки выпуска без выполнения команды,
а также отдельный явно синтетический общий пример в режиме просмотра.

При фактической CSS ширине 360 px `document.scrollWidth` равен 360 px,
диалог дела также имеет ширину 360 px. Обнаруженные проблемы с optional
запросом графика ПТО, пустым заголовком уведомления и неверными сообщениями
пустого фильтра/скрытой истории исправлены и повторно проверены.
Форма архивирования передаёт явное подтверждение открытых дел; связка реальной
формы с типизированным транспортом проверена UI-тестом. Подпись пустого изменения
статуса в истории отображается по-русски.

Browser file picker не завершил выбор файла; полноценную браузерную загрузку
через него не заявляем. Multipart upload проверен HTTP-тестами. Ссылка точной
страницы открыла blob image, но автоматизация запрещает читать вкладки с
протоколом blob; точные bytes и авторизация подтверждены HTTP-тестами.

## Повторение локального QA

`tools/customer_control_demo.py --seed-only` создаёт новую одноразовую БД и
private storage; без этого флага поднимает только localhost server.
`--resume-root /private/tmp/ltc-customer-qa.…` сохраняет ранее созданные
синтетические задачи, подачи, доказательства и JWT secret. Общий manifest
содержит только IDs отдельного синтетического примера, созданного самим tool;
перезапуск не включает в него найденные неизвестные строки.

Для повторения полного backend прогона запускайте pytest из новой приватной
временной папки с allowlist окружения, `POSTGRES_HOST=127.0.0.1`,
`POSTGRES_PORT=9`, временными storage/config roots и явными
`CUSTOMER_CONTROL_TEST_DATABASE_URL` и `MANAGEMENT_TEST_DATABASE_URL`,
указывающими на собственный disposable PostgreSQL с именем БД `test_*`.
Без этих двух opt-in переменных соответствующие PostgreSQL тесты пропускаются.

Mypy запускался из установленного локального runtime:
`/opt/anaconda3/bin/mypy --python-executable .venv/bin/python --follow-imports=silent`
для `access_policy`, `incident_workflow`, `control_releases`, `deadlines`,
`document_context`, API `customer_control`, `source_shares`, `collaboration`,
`organizations`, `assignments` и `schemas/customer_control`. Это проверка указанных
модулей, а не заявление о строгой типизации всего прежнего Python-кода.

Развёртывание, ограничения миграции и безопасный откат описаны в
[операционном руководстве R1](../customer-control-r1-operations.md).

## Роли на заставке и актуализация README

«Рабочий кабинет». Один загрузчик назначений теперь обслуживает и заставку,

заставки используют выбранное назначение и реальные ID камер; ПТО не запрашивает
недоступные ему график, камеры и оперативные события.
