Команда полного теста из `backend` (только для описанной тестовой БД):

```sh
POSTGRES_PORT=55433 POSTGRES_PASSWORD=management-test-local POSTGRES_DB=management_migration_test MANAGEMENT_TEST_DATABASE_URL=postgresql+psycopg://management_test:management-test-local@127.0.0.1:55433/management_migration_test .venv/bin/python -m pytest -q -rs

Остальные настройки тестового пользователя берутся из локальной конфигурации; на другой машине задайте также `POSTGRES_HOST=127.0.0.1 POSTGRES_USER=management_test`. Тестовый пароль публичный и относится только к disposable контейнеру.

Deterministic выбран явно, поэтому пропуск LLM не является деградацией этих запусков. [Журнал](../data/demo_management/queue_measurements.json) содержит UUID и состояния. Ранняя попытка с management key: **1.869 с**, три обращения, все `provider_auth_error` (401 `User not found.`), запуск partial, деградация 1/1. Дополнительный минимальный диагностический completions запрос тоже вернул 401; `/auth/key` ответил 200. Успешной генерации нет, usage не получен, стоимость не вычислялась. Отсутствие usage не доказывает нулевые расходы. Повторы остановлены.

Уточнение причины при завершающем аудите: оба бесплатных `/api/v1/auth/key` и `/api/v1/key` вернули 200 с JSON data; `is_management_key=true`, `is_provisioning_key=true`. Формат ключа верный, лишних пробелов нет. [Management key](https://openrouter.ai/docs/guides/overview/auth/management-api-keys) предназначен для административных операций и не допускает completions. Это была конкретная причина раннего отказа, а не доказательство неисправности обычного ключа. Добавлена бесплатная команда `python -m app.scripts.check_management_provider`; она не выводит реквизиты, не создаёт ключи и не вызывает модели. На том этапе требовался обычный ключ; позже пользователь предоставил его, доступ исправлен. Временные внешние ключи не создавались.

## Готово и частично

Готов локальный сквозной путь с четырьмя явно подписанными демонстрационными эпизодами, неизменной историей, точным расчётом, API, реальной очередью, UI и тремя отдельными LLM адаптерами/валидаторами. Реальные источники нормализуются по БД и проверяются тестами; реального полевого набора нет. Основной демонстрационный путь работает без внешнего провайдера, как предусмотрено планом.

Частично: рецензент живого LLM анализа требует подтверждения доступности техники и фактической загрузки; UI редактирует численные допущения, сложный реальный профиль/граф готовится через API. История одного объекта доступна, общего ранжирования нескольких объектов и сводной денежной суммы нет. Поручения и проверка реакции не реализованы: это следующий приоритет из плана. Во всех карточках действие остаётся предложением.
