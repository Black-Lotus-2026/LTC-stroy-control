# Исследование «Строй-контроля» перед доработкой UI

Дата: 16 октября 2026. Исследуемый коммит: `817f7bf`.
Основной пользователь: **инженер технадзора / оператор** — подтверждено владельцем задачи.
Запрос: простой ежедневный интерфейс с возможностью подробной настройки.

Это результаты исследования и предложение для обсуждения. Продуктовый код в ходе исследования не менялся.

## 1. Что требуется от решения на хакатоне

Исходное ТЗ удалено последним коммитом, но сохранилось в `HEAD^`:
`7. Департамент градостроительной политики города Москвы.pdf`.
Восстановленная локальная копия: `scratch/ui-audit/hackathon-task.pdf`.

ТЗ требует прототип, который распознаёт технику на снимках, связывает наблюдения с этапами календарного плана и объясняет отклонения. В качестве примера приведён котлован: экскаватор виден, самосвалы не замечены — нужно показать предупреждение, зону и подтверждающие снимки.

Для UI особенно существенны критерии раздела 8: явная и проверяемая связь наблюдений с планом, понятность и обоснованность предупреждений, простота быстрой оценки состояния стройплощадки. Количество экранов и эффектность диаграмм сами по себе задачу не решают.

**Основная цепочка демонстрации и ежедневной работы:**

`План → этап на момент наблюдения → ожидаемая техника → фактические наблюдения → объяснение отклонения → проверка оператором → отчёт`.

ТЗ допускает снимки и минимальный интерфейс; развитые RTSP-видеонаблюдение, управление сроками и многопользовательская платформа — расширения команды. При нехватке времени нужно сначала сделать эту цепочку достоверной на воспроизводимом наборе снимков или видео.

## 2. Как устроен проект

- Frontend: React 19, TypeScript, Vite 6, обычный CSS, без UI-библиотеки и маршрутизатора.
- Реальная точка входа: `src/main.tsx` → `src/App.tsx` → `src/styles.css`.
- `src/App.tsx` содержит 6437 строк: страницы, диалоги, состояние приложения, видеоплеер, формирование нарушений, HTML печатного отчёта.
- `src/api/stroyControlApi.ts`: 1320 строк; типизированные HTTP-запросы, перевод классов, локальные overrides, демонстрационные подстановки при ошибках.
- `src/components/DarkLayout.tsx`, `VideoPlayer.tsx`, `StageAnalytics.tsx`, `GanttChart.tsx`, `IncidentAlerts.tsx` образуют другой вариант интерфейса. `DarkLayout` не подключён к реальному `App`. Изменения только в этих компонентах пользователь не увидит.
- Backend: FastAPI, SQLAlchemy, PostgreSQL, Alembic, Celery/Redis, каталог работ, сопоставитель этапов, детектор, правила, хранение снимков.
- Данные: `data/work_catalog.xlsx`, `info/final_pars.csv`; копии CSV есть и под `backend/`.
- Обученных весов `.pt` и готовых видеопримеров в checkout нет. Генератор демо-плана есть.

## 5. Подтверждённые проблемы, которые влияют на новый UI

### P0. Вывод об отсутствии техники делается при неработающем детекторе

**Воспроизведение:** добавить заведомо недоступную RTSP-камеру `rtsp://127.0.0.1:1/unreachable-audit`. API сообщает `model_ready=false`. UI показывает `ultralytics is not installed`, но через окно наблюдения формирует «Нет необходимой техники: Башенный кран» и предупреждения по рекомендованной технике. События записываются в БД.

**Причина:** `CameraFrame` передаёт пустой массив детекций в `onFrameAnalysis` и при `model_ready=false` (`src/App.tsx:498`); `handleFrameAnalysis` считает этот результат достоверным отсутствием (`src/App.tsx:5038`).

**Требование к доработке:** различать «не замечена после корректного анализа», «модель недоступна», «нет свежего кадра», «источник отключён», «недостаточно данных». При неисправном анализе не создавать отклонения по составу техники.

### P0. RTSP LIVE фактически показывает встроенное фото

**Воспроизведение:** тот же недоступный URL отображается как «В сети», `RTSP LIVE STREAM`, 1080p/25 FPS/88 мс. В DOM источник картинки — `/src/assets/construction-camera.png`.

**Причина:** RTSP-ветка `CameraFrame` использует импортированное изображение (`src/App.tsx:598`). Телеметрия записана в JSX. Кроме того, снимки отдельных камер могут обрезаться по имени камеры (`src/App.tsx:438`), что не является реальным отличием ракурсов.

**Требование:** либо реализовать действительное преобразование RTSP в поддерживаемый браузером поток, либо явно отделить демонстрационный источник. Состояние «Камера добавлена» должно отличаться от «Получен свежий кадр». Не выдавать подстановку за доказательство.

### P0. Ручное подтверждение не сохраняется

**Воспроизведение:** для созданного через API инцидента выбрать «Подтверждено». UI показывает успех. Запрос `/api/v1/incidents/INC-DF11/status` получает **422**. В БД остаётся `pending`.

**Причина:** API возвращает UUID и человекочитаемый `code`. При преобразовании в `Incident` UUID теряется: `id: item.code` (`src/App.tsx:4453`). Обработчик передаёт этот код в UUID-endpoint и скрывает ошибку (`src/App.tsx:4898`, `backend/app/api/v1/incidents.py:357`). При создании в браузере также остаётся локальный случайный код вместо серверного идентификатора.

**Требование:** хранить отдельно `id` и `code`, связывать локальное создание с ответом сервера; показывать подтверждение сохранения либо ошибку с повтором. Оператор должен доверять выполненному действию после перезагрузки.

### P0. Контекст объекта теряется в событиях и видео

**Воспроизведение:** создать второй объект без камер и графика, открыть «Отчёты». В нём остаются события первого объекта.

**Причина:** `fetchIncidents()` вызывается один раз без `project_id` (`src/App.tsx:4453`). Смена объекта обновляет зоны/камеры/план, но не события (`src/App.tsx:4668`). Создание ряда событий и загрузка видео не передают активный `project_id`; backend выбирает первый проект. Наблюдения по источникам и загруженное видео также не полностью сбрасываются при смене объекта.

**Требование:** один явный контекст `projectId / zoneId / sourceId / observationTime`; загрузка и мутации всегда с ним. Сброс старых данных и защита от запоздавших ответов предыдущего объекта. Фильтр зоны должен действительно фильтровать наблюдения и события.

**Смежный серверный риск:** анонимный `GET /projects` возвращает объекты; ряд операций не проверяет пользователя/владельца. В тесте без токена получены оба тестовых объекта. Роли и границы доступа нужно обеспечить на сервере до обещания изоляции рабочих областей.

### P0. Время записи не управляет выбором этапа

**Воспроизведение:** загрузить видео со стартом `2026-05-05T10:00`. На эту дату в демо-плане идут земляные работы. UI сообщает «синхронизировано», но показывает октябрьскую кладку стен.

**Причина:** реальный `Monitoring` и обработчик нарушений используют `getCurrentStageByDate(stages)` с текущим временем. Результат `uploadVideoAsset` с `video_id` не сохраняется для синхронизации (`src/App.tsx:4862`). Сервис `/videos/{id}/sync` существует, но реальный `App` его не использует. Линия «сегодня» Ганта и статусы при импорте основаны на 24 сентября (`src/App.tsx:1852`, `backend/app/services/schedule_engine.py:172`), тогда как шапка показывает 16 октября.

**Требование:** единственная дата наблюдения. Для live — время свежего кадра; для записи — время начала плюс позиция воспроизведения. Вне интервала плана показывать «Нет активного этапа», не подбирать первый этап молча. Не маркировать прошедший по календарю этап фактически завершённым без отдельного подтверждения.

### P1. Экспорт по датам не фильтрует записи

**Воспроизведение:** указать 1–2 января 2000 года. Сегодняшний инцидент остаётся выбранным: «Будет выгружено в PDF: 1 из 1».

**Причина:** `rangeMatchedIncidents` проверяет слова «Вчера», «сен», «д» в строке `inc.time`, а `exportStartDate`/`exportEndDate` не используются для сравнения (`src/App.tsx:2669`). При маппинге инцидента полная дата уже потеряна — остаётся HH:mm.

**Требование:** сохранять ISO timestamp, фильтровать по действительному интервалу в часовом поясе объекта. Отдельно проверить переходы суток и границы смены. В текущей реализации кнопка PDF вызывает браузерную печать — подпись должна это честно объяснять.

### P1. Несколько источников правил дают противоречивые требования

Профиль в «Аналитике», список обязательной техники справа, подсказка Ганта и генератор нарушений используют разные функции и данные. Например, в аналитике погрузчик с 80% рекомендован, а справа перечислен как обязательный. После перевода башенного крана в «Допустимая» API ответил 200, но блок обязательной техники на наблюдении продолжил его показывать.

**Источники:** `getRequiredMachineryForStage` (`src/App.tsx:127`), `getStageMachineryRules` (`:160`), `getEffectiveStageRules` (`:225`), серверный профиль (`backend/app/api/v1/schedule.py:250`). Есть и переопределения в `localStorage`, включая ключ по имени этапа.

Документация задаёт пороги 80/50/20%, код API и `RuleEngine` — >80/60/15%. В UI обещано 10 классов, фактический словарь детектора содержит 11. Нужны один профиль правил, согласованный справочник и единые подписи. Проценты ожидаемости техники по методике следует отделить от уверенности распознавания конкретной рамки.

### P1. Ошибки и демонстрационные данные маскируются успехом

- Если API недоступен, `fetchIncidents` возвращает `INC-042`/`INC-043` с демонстрационными фото. После запуска API и регистрации они продолжали отображаться, хотя база была пустой. Это прямо воспроизведено.
- `loadDemoSchedule`, `uploadVideoAsset`, ручные настройки и некоторые операции имеют локальные fallback-ветки, не всегда отличимые от сохранения на сервере.
- «Снимок» и «Сформировать отчёт» на наблюдении только показывают toast (`src/App.tsx:930`, `:1078`). Кнопка снимка проверена в браузере.
- «Система активна» и «Данные актуальны · 8 сек» — постоянные подписи (`:5772`, `:5961`), не результаты health/freshness.
- При ошибке загрузки доказательства подставляется общий кадр стройки. Для доказательной базы нужен явный статус отсутствующего фото.

### P1. Фоновый мониторинг зависит от открытого экрана

Камеры опрашиваются и нарушения формируются внутри React-компонентов наблюдения. При переходе на другой раздел компоненты размонтируются; закрытие вкладки останавливает этот путь контроля. Настроенный beat содержит только heartbeat; воркерный модуль не подключён как непрерывный сбор всех камер.

До переноса конвейера на сервер необходимо явно обозначать режим интерактивного анализа. Постоянный мониторинг, дедупликация и журнал должны жить независимо от маршрута браузера. Иначе упрощение навигации меняет само поведение контроля.

### P2. Плотность, адаптивность и навигация

- Два верхних уровня управления объектом плюс отдельный список камер занимают много места; кнопки добавления дублируются в нескольких блоках.
- Обязательная информация и технические подробности визуально почти равнозначны. Много текста 9–11 px, капса, англоязычных ERROR/WARNING/YOLO/STAGE MACHINERY SERVICE.
- Фотоархив и отчёты повторяют одну сущность — событие, а настройки правил скрыты под названием «Аналитика».
- Радар дублирует таблицу и не отвечает на основной вопрос оператора о текущем отклонении.
- Нет ссылок на конкретные страницы/объекты/события; `page` живёт в `useState`, перезагрузка возвращает наблюдение.
- На 375 px контент выходит до 483 px, боковая панель перекрывает рабочую область. Основная камера оказывается ниже нескольких блоков управления.
- Проверенные диалоги камеры и альбома не имеют `role="dialog"`/`aria-modal`; нет полноценного управления фокусом. Положительные элементы уже есть: часть aria-label, focus-visible и prefers-reduced-motion в CSS.

## 6. Предлагаемая структура: просто снаружи, подробно по запросу

Рекомендация: **рабочее место оператора с раскрываемыми деталями**. Не делать глобальный переключатель «новичок/эксперт», который создаёт два разных интерфейса. Основные действия постоянны; сложные параметры открываются из относящегося к ним объекта.

### Основная навигация

| Раздел | Содержание |
| --- | --- |
| Мониторинг | Состояние объекта, текущий этап, ожидается/замечено, источники, новые отклонения |
| События | Единый журнал, фильтры, карточка и фотоальбом, ручная проверка, экспорт |
| План работ | Этапы, сроки, Гант по запросу, импорт с проверкой, требования к технике выбранного этапа |
| Настройки | Источники, зоны, параметры контроля, сведения об объекте; доступ по роли |

Фотоархив становится вкладкой/блоком доказательств события. Отчёт — действием над отфильтрованным журналом. Текущая «Аналитика» превращается в «Требования к технике» выбранного этапа, а дополнительные графики остаются раскрываемыми деталями.

### Главный экран

1. **Одна шапка:** объект, зона, режим «Сейчас / Запись», время анализируемого кадра.
2. **Короткий статус:** «Требуют проверки: N», «Источники: M из K доступны», «Последний корректный анализ: …». Отдельное состояние «Контроль недоступен» с причиной.
3. **Текущий этап:** понятное название, сроки, ссылка «План и требования».
4. **Сравнение техники:** строки «Техника / Требование / Наблюдение / За какой период». Пример: «Самосвал / Обязательная / Не замечен / 30 секунд». Не превращать отсутствие наблюдения в доказанное отсутствие на всей стройке.
5. **Видео и доказательства:** один крупный кадр, компактный выбор источника, время и рамки. Сетевые URL, модель и диагностика — в деталях.
6. **Очередь отклонений:** причина, время, источник, снимок, статус проверки. Выбор открывает карточку рядом; не требует искать ту же запись в другом разделе.

Для ноутбука — две колонки: наблюдение/сравнение и очередь событий. Третью постоянную колонку камер убрать. Для телефона — последовательный поток с рабочим меню и без горизонтальной прокрутки всей страницы.

### Карточка события

- Что не совпало и на каком этапе.
- Что требовалось по правилу и что действительно наблюдалось.
- Интервал, источники, качество данных и ограничения вывода.
- Снимки всех действительных источников с временем каждого кадра; отметка, какой снимок идёт в отчёт.
- Действия: «Подтвердить отклонение», «Ложное срабатывание», «Оставить на проверке»; комментарий при решении.
- Серверное состояние сохранения и история решения. Простой статус события не должен одновременно играть роль тяжести, назначения и готовности данных.

### Первый запуск

Показывать последовательность: **объект → загрузить и проверить план → добавить источник → проверить готовность → начать анализ**.

На пустом объекте не показывать обязательный кран, активный мониторинг и фиктивные нарушения связи. Демо-запуск — отдельное явное действие со своей пометкой; боевые и демонстрационные данные не смешивать.

## 7. Какие подробные настройки нужны

| Уровень | Что дать пользователю | Текущее положение |
| --- | --- | --- |
| Этап | Категория техники, обоснование требования, источник профиля, сброс ручных изменений | Категории и сброс есть, нужно согласовать данные и разместить рядом с этапом |
| Источник | Название, зона, URL/тип, проверка свежего кадра, подключение/отключение, диагностика | CRUD есть; достоверный статус и RTSP требуют работы |
| Запись | Дата/время начала, часовой пояс, позиция, сопоставленный этап | Ввод есть, сквозной синхронизации в реальном App нет |
| Контроль | Окно накопления наблюдений, порог уверенности распознавания, условия недостаточности данных | Окно есть глобально в памяти процесса; остальные параметры частично фиксированы |
| События | Группировка повторов, пауза повторного уведомления, тяжесть, история решения | Непрерывного устойчивого механизма в текущем браузерном пути нет |
| Зоны | Привязка источников и этапов; область контроля | Сущности есть; фильтрация и использование зоны требуют интеграции |
| Отчёт | Период, зона/объект, статусы, снимки, состав акта, предварительный просмотр | Большая часть формы есть, временная фильтрация сломана |

Не добавлять все эти поля в первый экран. Параметры должны иметь единицы измерения, значение по умолчанию, объяснение эффекта и явную область действия. Изменения, влияющие на контроль, сохраняются на сервере, с отметкой автора/времени и версией правил.

Минимальное количество машин, расписание смен, исключения, маски зон и специальные профили — возможные расширения после проверки потребности. Поля количества и порогов частично заложены в модели БД, но их наличие не означает готовый UI/API-конвейер. Нельзя просто суммировать количество одной машины с нескольких камер: для количественного контроля потребуется решить повторный учёт.

## 8. Как выполнять доработку

1. **Согласовать достоверность данных.** Исправить UUID/code, границы объектов, время наблюдения, единый профиль правил и состояния готовности. Запретить нарушения при неисправном анализе; отделить демонстрационные подстановки. Эти изменения требуют координации с backend/CV.
2. **Собрать основной сценарий оператора.** Единая шапка и контекст, мониторинг с ожидается/замечено, журнал событий и карточка, проверка с действительным сохранением.
3. **Разложить сложность.** Подробности камеры, этапа и правил в контекстных панелях. Объединить журнал и доказательства; перенести экспорт к событиям. Добавить первый запуск и проверку импорта.
4. **Привести интерфейс к единой системе.** Сохранить узнаваемость тёмной темы, увеличить рабочий текст и интервалы, убрать технические рекламные подписи и дублирование действий. Затем адаптивность и клавиатура.
5. **Зафиксировать демонстрацию.** План + видео/снимки с правильным временем + понятное отклонение + подтверждение + отчёт. Использовать настоящие веса и разнообразные примеры для отдельной CV-проверки.

Реальные компоненты стоит извлекать из `App.tsx` постепенно по изменяемым сценариям: `AppShell`, `ProjectContext`, страницы, `EventDetails`, `SourceViewer`, `ControlSettings`, клиент API. Не переносить старую логику в новые красивые компоненты без единого источника состояния. Не переписывать весь backend и все страницы одновременно.

Альтернативы: косметическая правка быстрее, но оставляет недостоверные сценарии; полная новая платформа расширяет объём задачи и риски. Предлагаемая последовательность сохраняет существующие возможности и делает основной путь понятным и проверяемым.

## 9. Приёмка будущей доработки

- Оператор на первом экране понимает состояние объекта, активный этап, причину отклонения и следующее действие.
- Пустой объект и неисправная модель не выглядят как корректный мониторинг с нарушениями.
- Все страницы и экспорт используют один объект, зону и дату наблюдения.
- Видео от 5 мая выбирает майский этап; вне плана показано отсутствие активного этапа.
- Правило, изменённое у этапа, одинаково показано в мониторинге, Ганте и объяснении события.
- Решение по событию сохраняется и остаётся после перезагрузки; сетевой сбой виден пользователю.
- События первого объекта не появляются во втором, включая переходы во время незавершённых запросов.
- Диапазон отчёта за 2000 год исключает события 2026 года.
- Недоступное доказательство не заменяется посторонней фотографией.
- Анализ выполняется независимо от открытого раздела либо интерактивный режим явно обозначен.
- Основной сценарий работает на 1366×768; на 375 px меню не перекрывает контент и нет горизонтального overflow страницы.
- Диалоги работают с клавиатуры, имеют название, управление фокусом и закрытие с возвратом фокуса.

## 10. Локальный стенд после исследования

Frontend: `http://127.0.0.1:5173/`. API: `http://127.0.0.1:8000/docs`.
Тестовый пользователь: `ui_audit` (создан исключительно в отдельной исследовательской базе).

API и БД работают в контейнерах `ltc-ui-audit-api`, `ltc-ui-audit-db`, сеть `ltc-ui-audit`.
Остановить только этот стенд: `docker stop ltc-ui-audit-api ltc-ui-audit-db`.

В БД есть тестовые объекты, штатный демо-план, заведомо недоступная тестовая камера, явно тестовый инцидент и ошибочные события, созданные самим приложением во время проверки. Их нельзя использовать как доказательство качества CV или реальных нарушений.
