# Безопасность: демонстрация и перенос на сервер

## Что входит

Три сценария: человек в опасной зоне, техника в зоне прохода и техника в запрещённой зоне. Это кандидаты на проверку, а не автоматически доказанные нарушения. Детектор — единственная установленная YOLO; VLM для этого потока не вызывается.

Начальная нормативная база: 2 документа, 5 привязок требований, 3 категории возможной ответственности по КоАП. Проверенные источники, пределы применимости, редакции и неопределённость поправки ГОСТ описаны в [нормативном обосновании](safety-normative-basis.md). Каталог намеренно ограничен этими тремя сценариями. Для новых сценариев нужны отдельные проверенные требования и новая миграция.

## Перенос

1. Обновить main, установить приватные веса и backend `.env` по [инструкции модели](../backend/weights/README.md).
2. Сделать резервную копию действующей PostgreSQL. Применить миграции: `docker compose run --rm api alembic upgrade head`. В штатном compose API также выполняет upgrade при старте.
3. Запустить `docker compose up -d --build --force-recreate`. Миграция `20261019_1600` создаёт таблицы каталога, зон, временных наблюдений, событий и решений и загружает замороженную версию нормативной базы. Ключ OpenRouter для контроля безопасности не нужен.
4. Войти владельцем объекта или администратором, добавить камеры. Открыть «Безопасность» → «Зоны контроля».

Бинарный SQLite-экспорт каталога можно создать отдельно из backend:

```sh
python -m app.scripts.export_safety_catalog ../var/safety/catalog-2026-10-19.sqlite3
```

Это переносимый справочный снимок из таблиц `documents`, `requirements`, `sanctions`, `metadata`, **не рабочая БД приложения**. Существующий файл не перезаписывается. Рабочие зоны, события, JPEG-доказательства и решения хранятся в PostgreSQL и переносятся обычной резервной копией всей БД. Изменение каталога в будущем — отдельной миграцией; прежние события сохраняют свои снимки оснований.

## Показ на хакатоне

1. Выбрать камеру, сценарий и название зоны. Взять текущий кадр либо загрузить кадр с тем же ракурсом. Отметить минимум три точки и замкнуть зону; доступен ввод координат с клавиатуры.
2. Указать реальное основание площадки — номер, дату и пункт схемы движения, ППР или инструкции. Назначить действующего ответственного. Для запрещённой зоны явно выбрать исключения по классам либо оставить запрет всей поддерживаемой технике.
3. Проверить ракурс, подтвердить границы и включить контроль. После поворота/зума камеры зону выключить и настроить заново. Время наблюдения и порог confidence — настройки алгоритма, не нормативные допуски.
4. Для локального видео открыть запись обычным способом, затем в разделе безопасности выбрать камеру, с которой сделана запись. Без этой привязки видео распознаётся, но правила зон для него не применяются. Ракурс записи должен совпадать с ракурсом полигона.
5. Воспроизвести запись. Контроль работает по кадрам, пока открыт рабочий экран. Для события нужны минимум два разных кадра, временной порог и геометрически согласованные рамки. Разрыв свыше 15 секунд или несовпадение рамок начинают наблюдение заново. Кадры с обратным временем не учитываются; для повторного анализа откройте запись заново, начав новую сессию источника. Дубли отсеиваются, один непрерывный эпизод не создаёт карточку на каждом кадре.
6. В «Безопасность» → «События» открыть кандидата. Проверить первый и итоговый кадры, границы зоны, условия площадки, ссылки на пункты документов и возможную ответственность. Первый кадр показывается без рамок итогового кадра.
7. Ответственный, владелец объекта или администратор сохраняет подтверждение/отклонение с комментарием. Подтверждение доступно после открытия изображения; ошибка сохранения сохраняет введённый комментарий. Уже принятое решение не перезаписывается. В карточке остаются автор, время и комментарий.

## Границы доказательств

Проверяется нижняя центральная точка рамки в полигоне, а не метрическое положение объекта. Согласование рамок не является надёжным трекингом личности/машины. Присутствие в проходе не доказывает полную блокировку, присутствие в запрещённой зоне не доказывает момент въезда или отсутствие допуска. Начало и итоговый кадр фиксируются при создании кандидата; карточка не заявляет длительность после этого момента. Время источника передаётся клиентом и не считается доверенной судебной временной меткой.

Суммы штрафов не начисляются и не складываются. Система не подтверждает состав правонарушения. Ответственный проверяет применимость нормы; административное наказание назначает уполномоченный орган. Отсутствие событий, ошибка модели или отсутствие кадров не означают безопасную площадку.

## Проверка реализации

Backend ASGI/БД-тесты проверяют три сценария, авторизацию и изоляцию объектов, временные разрывы/дубли, геометрию, исключения классов, неизменяемые доказательства и аудит, миграцию upgrade/seed/schema/downgrade на SQLite. UI-тесты проверяют реальный API-клиент, перенос снимков норм и дат, bearer-доступ к JPEG, ошибки review и полигон. Дополнительно выполнен локальный smoke с настоящей YOLO на последовательных кадрах пользовательского видео, без внешней отправки изображений, и проверка браузерного редактора/решения. PostgreSQL-конкурентность следует проверить на подготовленном сервере: локальный Docker daemon во время проверки не отвечал.
