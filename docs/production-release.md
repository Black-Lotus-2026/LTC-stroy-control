# Выпуск R1 на HTTPS-сервере

Публичная страница: https://stroycontrol.pro. Образ сайта собирается из
`Dockerfile.public`: Vite создаёт `dist/`, Caddy раздаёт статику и направляет
`/api/*`, `/media/*`, Swagger и OpenAPI в API. `VITE_API_URL=same-origin`
сохраняет текущие HTTPS origin и порт браузера. Приватные файлы обслуживает API.

## Перед обновлением

1. Дождаться завершения параллельных изменений, зафиксировать общий состав
   выпуска и прогнать контракты, backend, frontend и сборку.
2. Сохранить старые образы по отдельным тегам, приватную серверную Compose
   конфигурацию, `.env`, рабочее дерево и текущую ревизию Alembic.
3. Проверить восстановление дампа в отдельную БД `test_*`, затем выполнить
   миграции новым кодом и сравнить старые IDs, роли, статусы, даты и хеши.
4. Проверить PostgreSQL guards и конкурентные сценарии на тестовых схемах.

## Переключение

- Каждый выпуск размещается в отдельном каталоге; существующие незакоммиченные
  серверные файлы сохраняются в прежней копии. Имя Compose-проекта остаётся
  `ltc-stroy-control`, чтобы сохранить именованные тома и сетевые имена.
- Серверная Compose-конфигурация хранится отдельно от Git и применяется с
  явным `--project-directory` каталога выпуска. Сохраняются рабочая БД,
  приватные хранилища, Caddy, сертификаты и `ENVIRONMENT=prod` у API и воркеров.
- Новый backend и web собираются до остановки приложения. Веса устанавливаются
  отдельно и сверяются с закреплённым SHA256; секреты не входят в Git.
- На время финального согласованного дампа БД и копирования закрытых файлов
  останавливаются API, планировщик и пишущие воркеры. Redis и его очередь
  сохраняются. Затем выполняются миграции и повторная сверка данных.
- API, воркеры и web запускаются одной версией. Проверяются HTTPS, health,
  readiness, закреплённая модель, защищённые файлы и параметры Secure-cookie.

Для MyVMS используются только серверные переменные из
[инструкции интеграции](myvms-live-demo.md). Проверка доступа к источникам
и кадрам не должна публиковать логины, пароли или полные адреса подключения.
Синтетические QA-аккаунты остаются в отдельной тестовой БД; администратор
в рабочей системе для проверки не создаётся.

После миграции `2000` неизвестные старые материалы общего демо закрыты
`demo_manifest=NULL`. Повторная публикация выполняется оператором по проверенным
IDs с проверкой зависимостей. Загрузка файлов сама по себе не публикует их.

## Откат

Если миграция ещё не выполнялась, можно вернуть прежний каталог кода и образы.
После изменения схемы нужен совместимый выпуск либо проверенная согласованная
копия БД и закрытых файлов до обновления. Перед восстановлением сохраняется
и состояние после миграции, чтобы не потерять новые решения пользователей.
Разрушительный `alembic downgrade` не используется.

Подробные правила переноса данных и ограничений доступа:
[эксплуатация R1](customer-control-r1-operations.md).
