# 0001. Выбор стека

**Решение.** Python 3.12, FastAPI, PostgreSQL + SQLAlchemy 2 + Alembic,
Celery + Redis, Docker Compose.

**Почему.**

*FastAPI* — схемы Pydantic и есть контракт с фронтендом: OpenAPI и
интерактивный Swagger генерируются из кода, поэтому документация API
физически не может разойтись с поведением API. При двух командах,
работающих параллельно, это главный аргумент.

*PostgreSQL* — данные сильно связаны (площадка → зона → камера → кадр →
детекция → инцидент), и почти каждый экран интерфейса требует агрегатов
и соединений. Документная база здесь дала бы только сложность.

*Celery + Redis* — обработка кадра не должна блокировать HTTP-ответ, а
проверка соответствия плану запускается периодически, сама по себе. Это
ровно та задача, для которой существует связка «очередь + планировщик».
Подробнее — [0002-celery.md](0002-celery.md).

*Docker Compose* — требование организаторов и, что важнее, гарантия, что
на машине жюри проект поднимется одной командой.

**От чего отказались.**

*MinIO/S3 на прототипе* — лишний контейнер. Кадры лежат на диске за
интерфейсом `Storage`; переезд на S3 — это новая реализация интерфейса,
без изменений в остальном коде.

*Асинхронный SQLAlchemy* — см. [0003-sync-sqlalchemy.md](0003-sync-sqlalchemy.md).

**Граница применимости.** Всё перечисленное рассчитано на масштаб прототипа:
одна площадка, единицы камер, кадры раз в несколько секунд. Для промышленной
эксплуатации на сотнях камер потребуется отдельное хранилище кадров (S3),
вынос очереди `cv` на машины с GPU и, вероятно, партиционирование таблицы
детекций по времени.
