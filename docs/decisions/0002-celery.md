# 0002. Celery: две очереди, задачи как обычные функции

**Решение.** Celery с брокером Redis. Две очереди: `cv` (детекция) и
`default` (правила, импорт, отчёты). Вся логика живёт в обычных функциях,
`@shared_task` — тонкая обёртка над ними.

**Почему две очереди.** Детекция тяжёлая и держит модель в памяти,
остальные задачи — секундные. В общей очереди генерация отчёта ждала бы
за десятком кадров, и интерфейс выглядел бы зависшим.

**Почему задачи — обёртки, а не логика.** Функцию `analyze_frame(frame_id)`
можно вызвать из теста, из скрипта и из консоли — без брокера и воркера.
Тот же код исполняется в проде и в тесте. Дополнительный эффект: настройка
`CELERY_EAGER=true` переводит систему в синхронный режим целиком, поэтому
отказ Redis во время демонстрации не блокирует показ.

**Правила, которые нужно соблюдать.**

1. Модель загружается один раз на процесс воркера, а не внутри задачи —
   иначе каждый кадр оплачивает загрузку весов.
2. Через брокер передаются только идентификаторы, никогда не изображения.
   Кадр читается воркером из хранилища по ключу.
3. Движок правил запускается **не на каждом кадре**, а периодически по
   каждой паре «зона × активная работа». Это даёт окно наблюдений, нужное
   для правил вида «техника не найдена в трёх последовательных наблюдениях»,
   и одновременно решает проблему дублирования инцидентов.

**От чего отказались.** От запуска правил синхронно после каждой детекции:
такой вариант порождает новый инцидент на каждом кадре и делает ленту
событий нечитаемой уже через несколько минут работы.
