# 0006. Контракт API с фронтендом

Записка появилась после того, как бэкенд и фронтенд свели в одну ветку
(`main`), а соединения между ними не возникло: интерфейс живёт на данных,
зашитых в `src/data.ts`, и ни одного сетевого вызова в нём нет. Это не
чья-то оплошность — на момент слияния у бэкенда не было ни одной бизнес-ручки,
подключаться было не к чему. Записка фиксирует правила, по которым ручки
появляются, чтобы вторая команда работала от документа, а не от догадок.

Источник истины — `/openapi.json`, он генерируется из кода и разойтись с
поведением API не может. Здесь только то, чего в схеме не видно: почему
именно так и что обещано не менять.

## Что обещано не менять

**Конверт списка.** Любая списочная ручка возвращает
`{"items": [...], "pagination": {"page", "page_size", "total"}}`, даже когда
элемент один. Голый массив в корне запрещён: добавить к нему счётчик потом
можно только сломав всех, кто уже разобрал ответ.

**Формат ошибки.** Всегда `{"error": {"code", "message", "details"}}`, на
любом коде состояния. `code` — машинный (`NOT_FOUND`, `VALIDATION_ERROR`),
на него можно ветвиться; `message` — русский текст, его можно показать
человеку, но разбирать нельзя; `details` — произвольный объект для
подробностей (например, список полей, не прошедших проверку).

**Время.** ISO 8601 с указанием пояса, всегда UTC (`2026-09-17T11:32:00Z`).
Относительные подписи — «8 мин назад», «просрочено на 19 мин» — считает
фронтенд: только у него есть часы пользователя. Исключение одно:
`is_overdue` у инцидента считает сервер, потому что расхождение часов
клиента и сервера не должно менять ответ на вопрос «просрочено ли».

**Единица измерения — в имени поля.** `confidence` — доля от 0 до 1 (в
таком виде её даёт детектор и хранит база), `visibility_percent` — целые
проценты. Поэтому «94%» в карточке инцидента — это `confidence: 0.94`, а
«обзор 72%» — это `visibility_percent: 72`. Приведение к одной единице
обсуждалось и отвергнуто: перевод долей в проценты при записи в базу
означал бы терять точность на каждом кадре.

**Идентификаторы.** Связи — по `id` (UUID). `code` (`INC-247`, `CAM-03`,
`A-03`) существует для людей: его показывают, по нему ищут, его называют
в разговоре. Строить на нём ссылки нельзя — коды переназначаются.

## Значения перечислений — латиницей, подписи отдаёт сервер

В базе и в API статусы выглядят как `pending`, `false_positive`,
`equipment_missing`. В интерфейсе они должны выглядеть как «Требует
проверки», «Ложное срабатывание», «Ожидаемая техника не найдена».

Переводить на сервере нельзя: значение уехало бы в фильтры, в ключи
объектов и в условия — и первая же правка формулировки («Требует проверки»
→ «На проверке») сломала бы фильтрацию. Держать словарь на фронтенде
тоже плохо: новый статус появляется в коде бэкенда без миграции (см.
[0004](0004-data-model.md)), и фронтенд узнает о нём, только показав
пользователю голое `equipment_insufficient`.

Поэтому словарь отдаёт сервер: `GET /api/v1/meta/dictionaries` возвращает
для каждого перечисления список `{value, label}` в порядке отображения.
Фронтенд запрашивает его один раз при загрузке и рисует подписи и фильтры
из ответа. Новый статус появляется в интерфейсе сам.

## Действия над инцидентом — отдельные ручки, а не PATCH

`POST /incidents/{id}/assign`, `/status`, `/comment` вместо одного
`PATCH /incidents/{id}`.

Причина в том, что это не правки полей, а события. Каждое пишет строку в
историю инцидента, и у каждого свои обязательные параметры: отклонение
требует причины из списка, устранение проставляет время. `PATCH` с телом
`{"status": "false_positive"}` пришлось бы валидировать по соседним полям,
и из схемы было бы не видно, что причина обязательна. Отдельная ручка
говорит это типом запроса.

Ответ на действие — инцидент целиком в новом состоянии, а не пустой `204`:
иначе интерфейсу пришлось бы делать второй запрос, чтобы показать результат.

## Фильтры

Query-параметры, повторяющиеся для множественного выбора:
`?status=pending&status=confirmed`. Списки через запятую отвергнуты —
разбор строки пришлось бы писать руками, а повторяющийся параметр FastAPI
разбирает и документирует сам.

Постраничная навигация — `page` (с единицы) и `page_size` (по умолчанию
50, максимум 200). Курсорная не взята намеренно: интерфейсу нужны номера
страниц и общее число записей, а объёмы прототипа этого не требуют.

## Объяснение инцидента — часть контракта

Поле `explanation` имеет фиксированную форму:

```json
{
  "summary": "Экскаватор не найден в трёх наблюдениях подряд",
  "factors": ["По плану активна работа «Разработка грунта»", "..."],
  "limitations": ["Камера видит 72% рабочей зоны"]
}
```

Форма зафиксирована здесь, до появления движка правил, потому что от неё
зависит вёрстка карточки. `limitations` — обязательная часть, а не
украшение: отсутствие техники на кадре не равно её отсутствию на площадке,
и интерфейс обязан это показывать рядом с выводом, а не прятать.

## Чего в контракте нет

**Аутентификации.** Ручки открыты, пользователь действия передаётся телом
запроса (`actor_user_id`). Для прототипа это осознанный размен: роли в
модели данных заложены, вход по паролю — работа, не влияющая на демонстрацию.
Граница применимости очевидна — наружу такой API выставлять нельзя.

**Живых обновлений.** Лента инцидентов обновляется опросом. WebSocket
потребовал бы асинхронного слоя доступа к данным, от которого мы отказались
по [0003](0003-sync-sqlalchemy.md); при опросе раз в несколько секунд
разница для демонстрации незаметна.
