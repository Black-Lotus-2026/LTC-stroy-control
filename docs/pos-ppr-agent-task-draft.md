# Агент техники этапов из ПОС и ППР

Статус: **реализовано для локальной проверки**. Модель вызывается через
внешний API. Правила ниже приняты как рабочие допущения и могут быть изменены
после проверки на реальном ПОС/ППР.

## Локальный запуск

1. Откройте `backend/.env` (если файла ещё нет, скопируйте
   `backend/.env.example`). Укажите `DOCUMENT_LLM_API_KEY` или
   `OPENROUTER_API_KEY`. Ключ не вставляйте в чат и не коммитьте. Значения по
   умолчанию: `DOCUMENT_LLM_BASE_URL=https://openrouter.ai/api/v1`,
   `DOCUMENT_LLM_MODEL=openai/gpt-4o-mini`.
2. Из корня проекта выполните `docker compose up --build -d`. API при старте
   применит миграции, а фоновый воркер обработает анализ. После изменения
   ключа перезапустите `docker compose up -d --force-recreate api worker`.
3. Откройте `http://localhost:5173`, выберите объект и загрузите график в
   разделе «Прогресс». Во вкладке «Документы» загрузите ПОС/ППР и нажмите
   «Проанализировать этапы». Проверьте цитаты и классы, затем выберите
   предложения и нажмите «Применить выбранные».
4. Если анализ не начинается, проверьте `docker compose logs --tail=100 api
   worker`. Сообщение о ненастроенном ключе появляется и в интерфейсе.

Для запуска через `docker-compose.public.yml` на сервере агентский ключ нужно
указать в корневом `.env` релиза как `DOCUMENT_LLM_API_KEY` или
`OPENROUTER_API_KEY`, затем пересоздать `api` и `worker`.

## Цель

Для этапов, загруженных из календарного плана Excel/CSV, находить требования к
строительной технике в документах ПОС и ППР конкретного объекта. Сопоставлять
найденную технику с классами, которые распознаёт CV-модуль, и показывать,
какие значения необходимости следует изменить по сравнению с текущей оценкой
по названию этапа и `info/final_pars.csv`.

## Вход и результат

- Вход: выбранный объект, его сохранённые этапы графика, загруженные ПОС/ППР.
- По каждому этапу: найденная техника, назначение (если оно явно указано),
  класс CV или отметка «не распознаётся», документ, местоположение и цитата.
- Сравнение: текущее правило этапа → предложенное правило → основание изменения.
- Если данных нет: «В загруженных документах не найдено подтверждения для
  этого этапа». Текущее правило остаётся прежним.
- История применения: какие классы изменены, на основании какого фрагмента,
  когда и кем. Повторный анализ после изменения документа или графика не
  должен незаметно менять уже применённые правила.

## Сценарий пользователя

1. Пользователь загружает график Excel/CSV обычным способом.
2. Во вкладке **«Документы»** выбранного объекта загружает ПОС/ППР. Форма
   показывает тип, имя и число извлечённых фрагментов; документы можно
   скачать и удалить. Документы принадлежат только этому объекту.
3. Нажимает **«Проанализировать этапы»**. Интерфейс показывает ход анализа и
   результат отдельно для каждого этапа. Ошибка одного этапа не скрывает
   результаты остальных.
4. Пользователь просматривает предложения и цитаты, затем явно выбирает и
   применяет нужные изменения.
5. После применения экран правил этапа и CV-контроль используют обновлённые
   значения. Можно увидеть источник каждого изменения и вернуть прежнее.

## Требования к агенту

1. Читать названия этапов из сохранённого графика и текстовые фрагменты
   документов, сохраняя страницу/таблицу/абзац как источник.
2. Искать технику только в контексте соответствующего этапа. Общий перечень,
   другой этап, отрицание и запрет не подтверждают необходимость техники.
3. Проверять, что каждая цитата дословно есть в указанном фрагменте и этот
   фрагмент принадлежит документу выбранного объекта.
4. Сопоставлять названия с каталогом классов CV, в том числе синонимы.
   Проверять поддерживаемый набор текущего обученного детектора. Неизвестные
   и неоднозначные названия оставлять
   на проверку.
5. Не делать вывода «не требуется» из отсутствия упоминания. Не подменять
   количественные требования вероятностью без явно согласованного правила.
6. Если документы противоречат друг другу или связь этапа с фрагментом
   сомнительна, показывать конфликт и не применять такой вывод автоматически.
7. Работать с настраиваемой моделью через API; ключ хранить только в
   конфигурации backend. При недоступности модели показывать понятную ошибку,
   сохраняя загруженные документы и действующие правила.

## Интерфейс

- Вкладка «Документы» в **новом интерфейсе по умолчанию**: загрузка, список,
  запуск анализа, обзор этапов и переход к цитатам. Место вкладки в навигации
  можно изменить при согласовании.
- Существующая панель документов в `#legacy` остаётся работоспособной;
  согласовать, нужен ли в ней тот же полный сценарий.
- На экране правил этапа различать источник значения: справочник, применённый
  результат документа или ручная правка.

## Что было в рабочей ветке до этой задачи

- Импорт графика и исходная оценка техники по названию этапа.
- Ручное изменение `schedule_tasks.machinery_probabilities`.
- Незакоммиченные загрузка ПОС/ППР/ТЕР, извлечение текста, поиск техники и
  проверка цитат для **одного этапа** в старом интерфейсе.
- Нет полного анализа графика, сопоставления найденного с классами CV,
  сохранённого предложения, применения изменений и вкладки в новом интерфейсе.
- Импорт графика записывает оценку по справочнику прямо в
  `machinery_probabilities`; ручное редактирование обновляет тот же словарь.
  Сейчас нельзя надёжно отличить исходную оценку от ручной правки по данным
  этой колонки. До применения предложений агента нужен отдельный источник
  происхождения правил и явный порядок приоритета.
- Каталог содержит 11 классов техники, но активный детектор может
  поддерживать только часть из них. Неподдерживаемый класс нельзя выдавать за
  действующее автоматическое правило контроля.

## Критерии приёмки

1. После загрузки графика и документа пользователь видит по всем этапам
   результаты с источниками либо явную отметку об отсутствии подтверждения.
2. Из явно подтверждённого названия техники получается допустимый класс CV;
   техника вне перечня или вне поддерживаемого активным детектором набора не
   попадает в автоматические правила контроля.
3. Применённое изменение сохраняется в БД и влияет на экран правил и
   последующую оценку кадров. Существующие инциденты не переписываются.
4. При отсутствии совпадения, неоднозначной цитате, конфликте документов или
   отказе модели действующие правила остаются прежними.
5. Пользователь другого объекта не может читать документы или применять
   результаты к чужим этапам.

## Рабочие решения для реализации

1. Агент создаёт предложения. Пользователь выбирает их на экране и нажимает
   «Применить». Изменение сохраняется в БД; доступна отмена применения.
2. Явная обязательность в цитате и согласующийся ответ модели дают статус
   «обязательная»; явная рекомендация — «рекомендованная». Нейтральное
   упоминание ничего не меняет. Подтверждённый документ может повысить или
   понизить исходную оценку справочника после подтверждения пользователя.
3. Ручная правка имеет приоритет над результатом агента. Противоречащие
   цитаты не применяются. ПОС и ППР не получают автоматического приоритета.
4. Принимаются текстовые PDF, DOCX, XLSX и TXT. Для сканов нужен OCR до
   загрузки. ТЕР может служить дополнительным источником, но для запуска
   требуется хотя бы один ПОС или ППР.
5. Полный сценарий размещён в новом интерфейсе по умолчанию. В `#legacy`
   остаётся ранее созданный поиск для одного этапа.
6. Модель подключается через настраиваемый внешний HTTPS API. По умолчанию
   используется OpenRouter; ключ задаётся в `backend/.env`. Провайдеру
   отправляются выбранные текстовые фрагменты документа и название этапа.
7. Повторная загрузка графика создаёт новые этапы; документальный анализ
   запускается заново. Старые результаты сохраняются в истории, но не
   применяются к новым этапам автоматически.

## Текущие ограничения

- Обученная CV-модель по умолчанию выполняет наблюдение без автоматического
  подтверждения отсутствия техники. Применённое документальное правило видно
  на экране этапа и сохраняется для дальнейшего контроля, но само по себе
  не включает выдачу нарушений по кадрам.
- Сопоставление редкого названия техники, предложенное только моделью,
  выделяется на экране и требует внимательной проверки пользователем.
- Без ключа внешнего API анализ не запускается; документы и действующие
  правила при этом остаются доступны.
