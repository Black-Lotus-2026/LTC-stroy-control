# Правила работы в этом репозитории

Сервис «Строй-контроль»: кадры с камер стройплощадки сопоставляются с
календарным планом работ, движок правил находит отклонения. Команда
Black Lotus, хакатон Департамента градостроительной политики Москвы.

Бэкенд (`backend/`) и фронтенд (корень: `src/`, `index.html`) делают разные
люди параллельно. Единственный контракт между ними — OpenAPI, который
генерируется из кода бэкенда: http://localhost:8000/docs

Прежде чем менять что-то заметное, прочитай
[docs/decisions/](docs/decisions/) — там записано, почему система устроена
так, а не иначе, и [docs/progress.md](docs/progress.md) — что сделано и что
в работе.

## Фронтенд: как обращаться к API

Полные правила — [docs/decisions/0006-api-contract.md](docs/decisions/0006-api-contract.md).
Ниже то, на чём проще всего ошибиться.

### Русские подписи статусов не пишутся на фронтенде

**Бери их из `GET /api/v1/meta/dictionaries`.** Эта ручка возвращает для
каждого перечисления список `{value, label}` в порядке отображения:

```json
{
  "dictionaries": {
    "incident_status": {
      "title": "Статус инцидента",
      "values": [
        { "value": "pending",   "label": "Требует проверки" },
        { "value": "confirmed", "label": "Подтверждено" }
      ]
    }
  }
}
```

Запроси её один раз при загрузке приложения и рисуй из неё и подписи, и
варианты фильтров. Так же устроены `incident_priority`, `incident_category`,
`incident_type`, `incident_event_type`, `reject_reason`, `camera_status`,
`zone_risk_level`, `schedule_task_status`, `object_category`, `ppe_status`,
`rule_kind`, `frame_source`, `frame_status`, `analysis_status`,
`evidence_kind`, `user_role`.

Почему так, а не словарём в коде фронтенда: набор статусов на бэкенде
меняется без миграции базы, почти каждый день. Свой словарь на фронтенде
отстанет молча — пользователь увидит голое `equipment_insufficient`, и
заметит это зритель демонстрации, а не разработчик. Обратный вариант,
когда сервер отдаёт сразу русский текст, отвергнут: тогда подпись уехала бы
в фильтры и в ключи объектов, и первая же правка формулировки сломала бы
фильтрацию.

В фильтрах, в условиях и в URL всегда используется `value` (латиница),
`label` существует только для показа человеку.

### Остальное, что нужно знать сразу

* **Списки приходят в конверте** `{"items": [...], "pagination": {"page",
  "page_size", "total"}}`, даже когда элемент один. Постранично —
  `?page=1&page_size=50`.
* **Ошибки всегда одинаковой формы** `{"error": {"code", "message",
  "details"}}` на любом коде состояния. Ветвись по `error.code`
  (`INCIDENT_NOT_FOUND`, `USER_NOT_FOUND`, `REJECT_REASON_REQUIRED`,
  `INCIDENT_STATUS_UNCHANGED`), `message` показывай, но не разбирай.
* **Время — ISO 8601 в UTC.** «8 мин назад» считает фронтенд. Единственное
  исключение — `is_overdue` у инцидента: его считает сервер, потому что
  часы клиента могут расходиться с серверными.
* **Единица измерения — в имени поля.** `confidence` — доля от 0 до 1
  (`0.94` показывается как «94%»), `visibility_percent` — уже проценты.
* **Множественный выбор — повторяющийся параметр:**
  `?status=pending&status=confirmed`, а не список через запятую.
* **Действия над инцидентом — POST на подресурс:** `/assign`, `/status`,
  `/comment`. Каждое возвращает инцидент целиком в новом состоянии, второй
  запрос за результатом делать не нужно. Перевод в `false_positive`
  требует `reject_reason`, в остальных случаях причина запрещена.
* **`explanation.limitations` обязательно показывать** рядом с выводом.
  Отсутствие техники на кадре не равно её отсутствию на площадке; система
  сообщает об ограничениях наблюдения, и прятать их нельзя — на этом
  держится проверяемость предупреждений.
* **Адрес API** задаётся переменной окружения сборки, а не зашивается в
  код. Бэкенд по умолчанию разрешает CORS для `http://localhost:5173`
  и `:4173`.

## Бэкенд: как здесь принято

* Логика живёт в `app/services/` обычными функциями; роутеры и Celery-задачи —
  тонкие обёртки над ними. Одну и ту же функцию должно быть можно вызвать из
  теста, из консоли и из задачи.
* Значения перечислений — латиница в нижнем регистре, хранятся строками.
  Новый статус — это правка `app/models/enums.py` **и** подписи в
  `app/services/dictionaries.py`; тест `test_dictionaries.py` не даст забыть
  второе.
* Ошибки домена бросаются как `AppError` с машинным кодом, а не как
  `HTTPException`: формат ответа один на всё API.
* Каждое изменение инцидента добавляет строку в `incident_events`. Менять
  поля инцидента в обход `app/services/incidents.py` нельзя — история и есть
  доказательство того, что отклонение довели до устранения.
* Решение, которое не очевидно из кода, записывается в `docs/decisions/`
  в момент принятия, а не задним числом.

Проверки перед коммитом:

```bash
cd backend && make test && make lint
```

Тестам, которым нужна база, она нужна по-настоящему: они выполняются в
отдельной схеме `test_api` и пропускаются, если PostgreSQL недоступен.
