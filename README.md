## Ключевые возможности и инновации

### 1. Синхронный мультикамерный анализ объекта
* **Анализ сразу всех камер на объекте:** Система обрабатывает не единичный изолированный ракурс, а **все подключенные видеопотоки и сетевые IP-камеры объекта одновременно**.
* **Единое агрегированное множество техники:** На строительной площадке одна камера неизбежно имеет «слепые зоны» (за перекрытиями, монолитными пилонами или бытовыми городками). Детекции со всех камер синхронно объединяются в **ОДНО общее множество для текущего этапа**, исключая слепые зоны и взаимно дополняя ракурсы.

### 2. Всеракурсная фотофиксация доказательств
* **Снимки со всех камер в момент проблемы:** В момент выявления технологического отклонения сервис мгновенно выполняет захват кадров со **всех активных камер** строительного объекта.
* **Мини-альбомы по ошибкам:** Снимки группируются в структурированный фотоальбом инцидента.
* **Иерархия отчетности:**
  * В сводный отчёт и экспресс-карточку выводится опорное фото с **первой (основной) камеры**, исключая дублирование одинаковых ракурсов;
  * При клике и переходе в фотоархив открывается **полный фотоальбом нарушения со всеми ракурсами**, позволяя инженеру технадзора всесторонне оценить ситуацию.

### 3. Интеллектуальный движок сопоставления с календарным планом
* **46 этапов и нормативный классификатор:** Модуль [`StageMatcher`](./backend/app/services/stage_matcher.py) автоматически связывает пользовательские наименования этапов из графика СМР с нормативным классификатором Мосгосстройнадзора (`info/final_pars.csv`).
* **Вероятностный профиль спецтехники:** Для каждого этапа рассчитывается технологический профиль:
  * **Обязательная техника (`MANDATORY`, $P \ge 80\%$)** — отсутствие влечет статус «Ошибка» (риск срыва темпа);
  * **Рекомендованная техника (`RECOMMENDED`, $50\% \le P < 80\%$)** — отсутствие влечет статус «Предупреждение»;
  * **Нехарактерная (лишняя) техника (`UNCHARACTERISTIC`, $P < 20\%$)** — фиксация влечет статус «Ошибка» о нарушении технологической дисциплины.
* **Темпоральный 30-секундный буфер:** Исключает ложные срабатывания при кратковременных технологических маневрах техники.

### 4. Изоляция рабочих областей и безопасность
* **Разделение рабочих областей:** Пользователи видят и администрируют только закрепленные за ними строительные объекты и камеры.
* **Ролевая модель:** Администраторы имеют сквозной мониторинг по всей Москве; инспекторы технадзора и подрядчики работают в изолированных пространствах.
* **Простой интерфейс:** четыре основных раздела, единый выбор объекта и компактная цена бездействия. Даты показаны у событий. [Текущее состояние, проверки и ограничения](docs/product-ui-review.md).

Сохранены backend анализа, три роли и сравнение сценариев. Контрольный пример даёт 44 000 / 68 000 / 112 000 ₽ и перенос 0 / 0 / 4 рабочих часа; 68 000 ₽ — условная разница, не фактическая экономия. Демонстрационные данные подписаны явно.

### Алерты и контроль устранения

В настройках объекта администратор выбирает ответственного и администратора для эскалации.
Там же задаются сроки для ошибок и предупреждений: по умолчанию 2 и 24 часа.
При регистрации нарушения система создаёт задачу ответственному и показывает её в разделе
«Алерты». Кнопка «Исправлено — проверить» запрашивает внеочередную проверку.
Celery Beat также запускает проверку по истечении срока. Воркер считывает новые кадры
с настроенных HTTP/MJPEG или RTSP камер и повторно применяет детектор. Если нарушение
исчезло, инцидент закрывается; если осталось либо камер/модели нет, руководитель
получает эскалацию. При недоступности камер результат проверки явно сохраняется как
«Нет данных», а устранение не подтверждается. Все действия доступны в истории инцидента.

Уведомления внутри приложения работают без дополнительных настроек. Для отправки
электронных писем укажите в `.env` значения `SMTP_HOST`, `SMTP_PORT`, `SMTP_FROM`
и при необходимости `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_STARTTLS`, затем задайте
email адреса пользователей в настройках. Пример переменных — в `backend/.env.example`.
Для автоматической проверки нужны доступные воркеру камеры и веса YOLO в
`YOLO_WEIGHTS_PATH`. Процессы `worker` и `beat` должны быть запущены.

### Прогноз погоды и предупреждения

Укажите адрес объекта в настройках (или при создании объекта). При первом
запросе прогноза система определяет место через
[Nominatim / OpenStreetMap](https://nominatim.org/release-docs/latest/api/Search/),
показывает найденный адрес в интерфейсе и сохраняет координаты в полях
`projects.latitude`, `projects.longitude`. Повторное определение места нужно
только после изменения адреса. Если адрес не найден, уточните населённый пункт,
улицу и номер дома.
На вкладке «Камеры» появится прогноз на сегодня и следующие шесть дней:
состояние погоды, минимальная и максимальная температура, осадки, снег,
порывы ветра и предупреждения. Данные предоставляет
[Open-Meteo](https://open-meteo.com/en/docs); запрос использует часовой пояс объекта.

При первом открытии вкладки прогноз запрашивается автоматически. Celery Beat
запускает обновление активных объектов с адресом каждый день в 03:00 UTC;
для новых объектов он сначала определяет место по адресу.
Кнопка «Обновить» позволяет запросить прогноз вручную. Для фонового обновления
нужны запущенные `worker` и `beat` и доступ к `api.open-meteo.com`.
Для первого поиска адреса API и воркеру нужен доступ к `nominatim.openstreetmap.org`.
По [правилам публичного сервиса](https://operations.osmfoundation.org/policies/nominatim/)
запросы к нему ограничены четырьмя в минуту на инсталляцию, включая плановое
задание. Найденный адрес кешируется в `projects`, поэтому повторные обновления
прогноза не вызывают повторный поиск адреса.

Прогноз хранится в PostgreSQL, в таблице `weather_forecasts`: одна запись на
объект и календарный день. Повторный запрос обновляет запись; сохраняются дата,
время получения, провайдер, код WMO, числовые показатели, описание условий и
список предупреждений. При смене адреса старый прогноз и кеш места удаляются.
При ошибке провайдера сохранённые данные не перезаписываются. Миграция:
`20261017_0900_weather_forecast.py` и `20261017_1000_weather_address.py`;
в Docker они применяются при запуске API.

Правила предупреждений: гроза или туман по коду WMO, осадки от 20 мм/сутки,
снег от 5 см/сутки, порывы ветра от 54 км/ч и минимальная температура не выше
0 °C. Эти метки помогают планировать работы и не создают инцидент о нарушении.
API: `GET /api/v1/projects/{project_id}/weather` читает сохранённые данные,
`POST /api/v1/projects/{project_id}/weather/refresh` запрашивает и сохраняет новый
прогноз. Оба запроса требуют авторизации и проверяют доступ к объекту.

Отчётный агент умеет формулировать сводку через OpenAI и LangChain.
Интеграция опциональна: без ключа отчёты строятся детерминированным
шаблоном. Настройка и границы передачи данных описаны в
[docs/report-agent.md](docs/report-agent.md#llm-через-langchain).

### Поиск техники в ПОС и ППР

В новом интерфейсе откройте вкладку «Документы»: загрузите ПОС или ППР и
запустите анализ этапов графика. Агент автоматически обновит подтверждённые
правила техники, покажет цитаты и список изменений; каждое можно отменить.
Агент использует внешний OpenAI-совместимый API; ключ задаётся в
`backend/.env` как `DOCUMENT_LLM_API_KEY` или `OPENROUTER_API_KEY`.
Для GigaChat 3 Ultra установите `DOCUMENT_LLM_PROVIDER=gigachat` и задайте
`GIGACHAT_CREDENTIALS` (ключ API физлица) в том же файле. Сертификат НУЦ
Минцифры находится в `backend/certs` и используется только для GigaChat.
Подробности, ограничения и шаги локальной проверки — в
[описании агента](docs/pos-ppr-agent-task-draft.md).

Остановить: `make down`. Полный список команд: `make help`.

## Перспективы развития (Roadmap)

Векторы дальнейшего масштабирования и развития функционала платформы:

1. **ИИ-агент автоматизированного планирования по ПОС и ППР**:
   - Автоматический семантический парсинг и анализ строительной документации: **Проекта организации строительства (ПОС)** и **Проекта производства работ (ППР)**.
   - Автономный агент извлекает ведомости потребности в машинах и механизмах, строительные генеральные планы (стройгенпланы) и формирует структурированный календарный график СМР с точной привязкой нормативной техники к пространственным зонам без ручного ввода.

2. **Интеграция мультимодальных моделей (VLM) для глубокого анализа проблем**:
   - Подключение Vision-Language Models (VLM) в качестве второго экспертного контура валидации аномалий.
   - VLM анализирует пространственный контекст всей сцены целиком, выявляя скрытые причины отклонений: технологические паузы (схватывание бетона, пересменка, ожидание армирования), погодные факторы (затопление котлована грунтовыми водами, наледь), пространственные конфликты смежных бригад.
   - Автоматическое составление развернутых экспертных заключений и рекомендаций для инженеров технадзора по оптимизации темпа работ.

3. **Бесшовная интеграция с ЕЦХД Москвы**:
   - Масштабирование на тысячи городских строительных объектов через интеграцию с Единым центром хранения данных города Москвы (ЕЦХД) и автоматической выгрузкой инцидентов в аналитические панели Стройкомплекса.

## Стек технологий

* **Computer Vision & AI:** Ultralytics YOLO (10 классов строительной спецтехники), PyTorch, OpenCV, Pillow, NumPy.
* **Backend:** Python 3.12, FastAPI, SQLAlchemy 2 (ORM), Alembic, Pydantic v2, ReportLab, Python-Docx.
* **Frontend:** React 19, TypeScript, Vite, Canvas Stream Renderer, Interactive Gantt Engine, CSS Variables.
* **Инфраструктура & Хранение:** PostgreSQL 16, Redis, Docker, Docker Compose, Nginx.
