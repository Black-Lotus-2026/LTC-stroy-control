# Строй-контроль

**Контроль подрядчиков от требования в ППР до приёмки устранения заказчиком.**

React 19 · TypeScript · FastAPI · PostgreSQL · Celery · YOLO

[Быстрый старт](#quick-start) · [Логины и роли](#accounts) · [Рабочий сценарий](#workflow) · [Docker](#docker) · [Проверки](#checks) · [Документация](#docs)

</div>

---

Заказчик видит риски своих объектов, проверяет обнаруженные события, назначает
ответственных и принимает результат. Подрядчик получает задачи в своей области,
подтверждает исправление и при необходимости оспаривает основание. Инженер ПТО
готовит проверенные требования по исходным документам.

> **ППР → проверенное требование → утверждение заказчиком → камера или запись →
> событие с доказательствами → ответственный → устранение → приёмка заказчиком.**

Бизнес-правила первого релиза определены в
[архитектуре контроля заказчика](docs/customer-control-architecture.md).
Фактические проверки и ограничения — в
[отчёте о проверке](docs/validation/customer-control-regressions.md).
README описывает текущее локальное дерево проекта; публикация и развёртывание
на рабочем сервере выполняются отдельно.

## Быстрый старт: локальная проверка ролей

Это изолированный стенд с настоящими аутентификацией и проверками доступа,
но синтетическими пользователями, ППР, доказательствами и задачами.
Он использует отдельные SQLite и private storage; рабочий `backend/.env`
и рабочую БД не читает. Внешние AI-провайдеры и SMTP выключены.

**Окружение:** macOS, Python **3.12+**, Node.js **22.13+ из ветки 22** и npm.
Версия Python задана в `backend/pyproject.toml`; зависимости frontend —
в `package-lock.json`. Если `backend/.venv` и `node_modules` уже подготовлены,
установку можно пропустить.

Из корня репозитория:

```bash
python3.12 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.txt
npm ci
```

**Терминал 1 — API и тестовые данные:**

```bash
backend/.venv/bin/python tools/customer_control_demo.py --port 8991
```

Для реальных демо-камер MyVMS добавьте `--myvms-demo` после настройки
закрытого файла подключения: [инструкция live-демо](docs/myvms-live-demo.md).

**Терминал 2 — интерфейс:**

```bash
VITE_API_URL=http://127.0.0.1:8991 npm run dev -- --host 127.0.0.1 --port 5193 --strictPort
```

| Адрес | Назначение |
| --- | --- |
| [127.0.0.1:5193](http://127.0.0.1:5193/) | Вход и рабочий интерфейс |
| [127.0.0.1:8991/docs](http://127.0.0.1:8991/docs) | Swagger локального QA API |
| [127.0.0.1:8991/api/v1/health](http://127.0.0.1:8991/api/v1/health) | Проверка процесса API |

Останавливайте оба процесса через **Ctrl+C** в соответствующих терминалах.

### Как сохранить начатую проверку

При новом запуске скрипт создаёт новый каталог
`/private/tmp/ltc-customer-qa.*` и печатает его путь вместе с учётными данными.
В нём лежат `jury.sqlite`, закрытые файлы и `qa-state.json`.
Чтобы продолжить прежние задачи и подачи, после остановки API запустите:

```bash
backend/.venv/bin/python tools/customer_control_demo.py --port 8991 \
  --resume-root "/private/tmp/ltc-customer-qa.<суффикс-из-предыдущего-вывода>"
```

Замените весь путь на фактический. Для создания данных без запуска HTTP-сервера
есть `--seed-only`. QA-скрипт предназначен для локальной проверки;
он не создаёт пользователей в Docker или на рабочем сервере.

## Вход и переключение ролей

1. Откройте [локальное приложение](http://127.0.0.1:5193/).
2. Введите логин и пароль из таблицы. На заставке проверьте свою роль,
   организацию, объект и краткое описание задачи.
3. Нажмите **«Перейти к решениям»** у управляющего, **«Открыть мои задачи»**
   у прораба или **«Открыть документы»** у ПТО.
4. Для смены аккаунта нажмите аватар справа сверху → **«Выйти»**.
5. Если у человека несколько назначений, выбирайте объект, организацию и роль
   на заставке или через меню объекта в верхней панели. При возврате на заставку
   сохраняется выбранное назначение. Для общего демо кнопка называется
   **«Открыть демонстрацию»**, изменения в нём отключены.

### Все локальные тестовые аккаунты

Эти известные пароли относятся **только к одноразовому QA-стенду**,
создаваемому `tools/customer_control_demo.py`.

| Логин | Пароль | Роль и сценарий проверки |
| --- | --- | --- |
| `qa_manager` | `LocalQa2026!` | Управляющий заказчика: задачи обоих подрядчиков, решения и приёмка |
| `qa_manager2` | `LocalQa2026!` | Второй управляющий: независимое рассмотрение споров |
| `qa_foreman` | `LocalQa2026!` | Прораб подрядчика №1: первая задача, устранение и оспаривание |
| `qa_foreman2` | `LocalQa2026!` | Прораб подрядчика №2: вторая задача; первая ему недоступна |
| `qa_pto` | `LocalQa2026!` | Инженер ПТО подрядчика №1: документы, требования и связанные основания |
| `qa_viewer` | `LocalQa2026!` | Наблюдатель: разрешённые материалы только для чтения |

В фикстуре все аккаунты имеют старое глобальное поле `viewer`.
Рабочие полномочия выдаются **явными назначениями**, поэтому это поле не должно
подменять роль в интерфейсе или выдавать доступ к чужому объекту.

У обычной установки нет универсального логина администратора.
Самостоятельная регистрация создаёт пользователя без полномочий на объекты.
Для работы нужны членство в организации, участие организации в объекте
и действующее назначение. Рабочие пароли и API-ключи в README не хранятся.

### Права и необходимость каждой роли

| Роль | Что может делать | Основные ограничения | Зачем нужна |
| --- | --- | --- | --- |
| **Управляющий заказчика** | Проверять риски своих объектов; утверждать требования; подтверждать или отклонять обнаружения; назначать подрядчика, исполнителя и сроки; раскрывать материалы; принимать исправление или возвращать с замечаниями | Только выданные объекты и полномочия; конфликт интересов при решениях; доказательства не удаляются | Принимает решения от лица заказчика и контролирует результат |
| **Прораб подрядчика** | Видеть опубликованные задачи своей организации в назначенной области; брать в работу; прикладывать собственные доказательства; подавать устранение; оспаривать; загружать свои записи по разрешённой политике | Не видит чужую ответственность; не отключает контроль, не меняет требования, не удаляет доказательства и не принимает своё устранение | Организует исправление на площадке и подтверждает выполненную работу |
| **Инженер ПТО** | Загружать ППР в свою область; проверять страницы, цитаты и применимость; готовить редакции требований и отправлять пакет заказчику; комментировать и оспаривать доступные основания | Нет утверждения в контексте инженера, управления камерами и общей оперативной очереди подрядчиков | Превращает документ в проверяемое основание контроля |
| **Наблюдатель** | Читать материалы в разрешённой области | Нет изменения данных, запуска анализа и принятия решений | Даёт доступ к наблюдению без выдачи рабочих полномочий |

ПТО заказчика и ПТО подрядчика выполняют одну документную функцию,
но видят разные области. Администрирование членства организации и право
создавать объекты задаются отдельно от рабочей роли.
Правило совмещения ПТО и управляющего у заказчика описано в §4.4
[архитектуры](docs/customer-control-architecture.md).

Сервер проверяет организацию, объект, конкретную запись и действие,
включая каждый доступ к оригиналу, фотографии, отчёту и диапазону видео.
Отзыв назначения закрывает доступ с прежним токеном.

## Рабочий сценарий

| Шаг | Кто действует | Результат |
| --- | --- | --- |
| 1. Загрузить ППР | ПТО | Сохранён приватный оригинал и его версия |
| 2. Проверить требования | ПТО | Зафиксированы точная страница, цитата, область и ограничения |
| 3. Утвердить выпуск | Управляющий | Проверенный набор требований включается в контроль |
| 4. Проверить обнаружение | Система → управляющий | Кандидат с доказательствами подтверждён либо отклонён |
| 5. Устранить | Назначенный прораб | Добавлены собственные материалы и отправлена подача |
| 6. Принять результат | Управляющий | Конкретная подача принята либо возвращена с замечаниями |

| Статус API | Значение |
| --- | --- |
| `pending` | Обнаружение требует проверки; нарушение ещё не подтверждено |
| `confirmed` | Заказчик подтвердил нарушение и назначил ответственность |
| `in_progress` | Задача в работе, в том числе после возврата |
| `remediation_submitted` | Исправление заявлено, ожидается приёмка |
| `resolved` | Для новых дел — заказчик принял конкретную подачу |
| `false_positive` | Обнаружение отклонено |

Возврат переводит дело в `in_progress`, сохраняя прежнюю подачу и замечания.
Открытый спор блокирует приёмку; решение принимает независимый управляющий.
Автоматическая перепроверка даёт дополнительную информацию, а окончательную
приёмку выполняет заказчик. Старое закрытие по прежнему процессу помечается
отдельно и не выдаётся за приёмку заказчиком.

### Что посмотреть при совместной проверке

- У управляющего — две учебные задачи; у каждого прораба — только своя.
- У ПТО — документы и требования, исходные страницы, документные комментарии.
- В карточке дела — основание ППР, доказательства, сроки и разрешённые действия.
- В цикле устранения — подача, возврат с замечанием и повторная отправка.
- В меню объекта — доступные назначения; общая демонстрация доступна для чтения.
- На телефоне — очередь, карточка и документная панель.

Учебная камера в QA-фикстуре **не подключена к реальному потоку**.
Пустой план и отсутствие кадров обозначены явно. Это стенд для проверки
ролей и взаимодействий, а не демонстрация полной обработки реальной стройки.

## Документы, камеры и доказательства

- ППР поддерживают приватные оригиналы PDF, DOCX, JPG и PNG, версии, разбор,
  цитаты и ссылки на конкретные страницы. Загрузка ограничена 50 МБ.
- Новый ППР или выпуск требований не переписывает исторические основания дел.
- Камеры и сохранённые записи используют защищённый доступ. Перенос камеры
  и восстановление ракурса требуют согласования.
- Учитываются качество наблюдения, покрытие, неподвижный кадр и повтор записи.
  **Недостаток кадров не доказывает отсутствие техники.**
- Повторные запросы и наблюдения защищены от создания дублей. Доказательства,
  отправленные подачи и история решений сохраняются.
- Общая демонстрация публикует только явно перечисленные в манифесте материалы;
  пользовательские загрузки автоматически в неё не попадают.

YOLO использует единственный закреплённый checkpoint
`construction-yolov8m-v2.pt`; файл не хранится в Git. Установка, SHA256,
поддерживаемые категории и ограничения описаны в
[карточке модели](backend/weights/README.md).
По умолчанию `CONSTRUCTION_POLICY=shadow`: детекции сами по себе
не означают разрешение на нормативные выводы. Качество модели,
покрытие и активные требования проверяются отдельно.

Для камер и видео используется YOLO. Фото может дополнительно обращаться
к VLM через OpenRouter при включённой настройке и подходящем результате YOLO.
В локальном QA внешние вызовы выключены.

## Полный локальный стенд в Docker

Compose поднимает PostgreSQL 16, Redis 7, API, Celery worker/beat,
отдельный PPR worker, Ollama с `qwen2.5:7b` и frontend.
Первый запуск модели требует загрузки; это отличается от быстрого QA выше.

Сначала подготовьте `backend/.env` из примера, сохранив существующий файл:

```bash
test -f backend/.env || cp backend/.env.example backend/.env
```

Проверьте `backend/.env` и установите приватные веса
по [инструкции модели](backend/weights/README.md).
Для окружения, доступного другим людям, задайте собственный `JWT_SECRET_KEY`
и согласованную конфигурацию инфраструктуры; Compose содержит настройки демостенда.
API автоматически выполняет `alembic upgrade head` при старте:
**существующую рабочую БД сначала резервируют и проверяют по руководству R1**.

После подготовки, из корня проекта:

```bash
docker compose config --quiet
docker compose up --build -d
docker compose ps
```

| Адрес / порт | Сервис |
| --- | --- |
| [localhost:5173](http://localhost:5173/) | Frontend Docker-стенда |
| [localhost:8000/docs](http://localhost:8000/docs) | Swagger API |
| [localhost:8000/api/v1/health](http://localhost:8000/api/v1/health) | Процесс API |
| [localhost:8000/api/v1/ready](http://localhost:8000/api/v1/ready) | Доступность БД и брокера |
| `localhost:5433` | PostgreSQL; внутри Compose — `postgres:5432` |
| `localhost:6380` | Redis; внутри Compose — `redis:6379` |

Тестовые `qa_*` аккаунты **не создаются** этой командой.
Их создание и проверка ролей доступны через изолированный QA-скрипт выше.

```bash
docker compose logs -f --tail=100
docker compose down
```

Обычный `down` сохраняет именованные тома. `down -v` удаляет их данные.
Короткие команды доступны через `make help`.

### Настройки и адрес API

| Настройка | Где задаётся | Назначение |
| --- | --- | --- |
| `VITE_API_URL` | Окружение Vite / корневой `.env` для Compose | Доступный браузеру origin API без `/api/v1`; `same-origin` использует origin страницы для прокси Caddy |
| `FRONTEND_HOST` | Корневой `.env` для Compose | Разрешённый домен Vite, без протокола и порта |
| `CORS_ORIGINS` | `backend/.env` | JSON-массив разрешённых origin frontend |
| `POSTGRES_*`, `REDIS_*` | `backend/.env` и явные `environment` в Compose | База и брокер; в обычном backend нет переключения на SQLite через `DATABASE_URL` |
| `JWT_SECRET_KEY` | `backend/.env` | Секрет подписи токенов |
| `PPR_STORAGE_ROOT`, `CAMERA_VIEW_STORAGE_ROOT`, `STORAGE_LOCAL_ROOT` | Backend и воркеры | Приватное хранение документов, ракурсов и материалов |
| `YOLO_WEIGHTS_PATH` | Backend и CV worker | Путь к закреплённому checkpoint |
| `PPR_PROVIDER`, `PPR_OLLAMA_URL`, `PPR_ANALYSIS_MODEL` | Backend и PPR worker | Провайдер разбора; Compose задаёт Ollama |
| `CONSTRUCTION_POLICY`, `CONSTRUCTION_APPROVED_CLASSES` | Backend и CV worker | Явная политика применения детекций |
| `PHOTO_VLM_ENABLED`, `OPENROUTER_API_KEY` | `backend/.env` | Необязательный внешний анализ фото |
| `REPORT_LLM_ENABLED`, `OPENAI_API_KEY` | Корневой `.env` / окружение Compose; при прямом запуске — backend | Необязательные формулировки отчётов |
| `SMTP_*` | Корневой `.env` / окружение Compose; при прямом запуске — backend | Необязательная почта; уведомления в приложении работают без неё |

Без `VITE_API_URL` frontend выбирает hostname страницы и порт API 8000.
Для публикации за Caddy задайте `VITE_API_URL=same-origin`: запросы идут на `/api/v1` того же origin, сохраняя HTTPS и порт страницы.
Для текущего QA на порту 8991 переменная обязательна.
После изменения адреса API перезапустите Vite или пересоздайте frontend.
При HTTPS API тоже должен быть доступен через HTTPS.
Подробности прокси и CORS: [frontend-deployment.md](docs/frontend-deployment.md).

Контейнер frontend сейчас запускает **Vite dev server**.
Команда `npm run build` проверяет production-сборку в `dist/`, но текущий
Compose сам по себе не превращается в production-раздачу статики.

## Проверки

### Frontend и контракты

Из корня проекта:

```bash
backend/.venv/bin/python scripts/generate_customer_contract.py --check
npm run typecheck
npm run lint
npm run test:ui
npm run build
```

Браузерные автотесты используют тестовые ответы API:

```bash
npx playwright install chromium
npm run test:browser
```

Запуск с существующим frontend и альтернативным Chromium описан в
[tests/browser/README.md](tests/browser/README.md).
Браузерные fixtures не заменяют проверку настоящих прав API и файлов.

### Backend

Запускайте `pytest` из отдельного временного каталога с `PYTHONPATH`,
указывающим на `backend/`, отдельными storage roots и очищенным окружением,
чтобы не загрузить рабочий `.env`. Подробный проверенный порядок —
в [отчёте R1](docs/validation/customer-control-regressions.md#повторение-локального-qa).

Полная проверка PostgreSQL требует **собственной одноразовой тестовой БД**,
а также `pg_dump` и `pg_restore`. Передайте её URL в
`CUSTOMER_CONTROL_TEST_DATABASE_URL` и `MANAGEMENT_TEST_DATABASE_URL`.
Имя БД должно начинаться с `test_` или заканчиваться на `_test`;
тесты создают и удаляют свои случайные схемы.
Без этих переменных PostgreSQL-проверки пропускаются.

После исправлений проверяются изоляция организаций и подрядчиков, отзыв доступа,
прямые API и GET/HEAD/Range, переходы статусов, споры, повторные команды,
точные страницы ППР и сохранность исторических оснований.
Даты и результаты фактических прогонов находятся в
[отчёте проверки](docs/validation/customer-control-regressions.md).
Наличие команды или теста в репозитории не означает успешный прогон на сервере.

## Обновление и откат

Для **R1 целиком** нужны согласованный выпуск backend/frontend/воркеров,
резервная копия БД и приватных файлов, проверка восстановления и миграций.
Подготовлены ревизии `20261020_1700`–`20261020_2000` поверх цепочки
записей и ППР `1300`–`1600`.
Они сохраняют старые данные и не выдают всем старым пользователям повышенные права.
Полный порядок: [эксплуатация, миграции и откат](docs/customer-control-r1-operations.md).

Только для **отдельного обновления интерфейса с уже совместимым backend**,
после публикации проверенного коммита и сохранения локальных правок на сервере:

```bash
git pull --ff-only origin main
docker compose config --quiet
docker compose up -d --build --no-deps --force-recreate --renew-anon-volumes frontend
docker compose ps frontend
docker compose logs --tail=80 frontend
```

Обновление только frontend не устанавливает новые API и миграции R1.
При полном откате сначала сохраняют состояние после миграции, затем восстанавливают
согласованную копию БД и файлов и переключают совместимые сервисы.
Разрушительный `alembic downgrade` для неизменяемой истории заблокирован.

Рабочий HTTPS-сервер использует отдельный образ `Dockerfile.public` и
`Caddyfile.public`, с `VITE_API_URL=same-origin`. Его серверная Compose-конфигурация
сохраняет закрытые тома, окружение `prod` и существующие параметры БД.
Порядок выпуска с репетицией миграций и откатом:
[обновление HTTPS-сервера](docs/production-release.md).
